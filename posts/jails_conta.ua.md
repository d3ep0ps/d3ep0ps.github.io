## 1. Стандарт FreeBSD: Jails

Ми починаємо з FreeBSD, тому що вона зробила це першою, і робить це найчистіше.

Якщо ви стежили за цією серією, ви можете пам'ятати встановлення **BIND** (DNS). У FreeBSD адміністратори, які піклуються про безпеку, десятиліттями інсталювали BIND у `chroot` або Jail. Чому? Тому що BIND обробляє ненадійні вхідні дані з інтернету. Якщо його зламають, ви хочете, щоб зловмисник опинився в пастці, в коробці, а не бродив по вашій кореневій файловій системі.

### Анатомія Jail

Jail — це **Системна Віртуалізація**. Вона ділить ядро з хостом, але має власні:

1. **Корінь Файлової Системи** (`/usr/jails/web01`)
2. **Віртуальний Мережевий Інтерфейс** (`epair0b`)
3. **Повністю Ізольований Мережевий Стек** (Може запускати власний VPN, Firewall тощо)

### 1.1 Проблема Кореневої Файлової Системи

Перш ніж ми зможемо запустити jail, у нас є проблема.
Jail потребує середовища. Коли ви входите і вводите `ls`, jail потребує бінарного файлу `/bin/ls` для виконання. Йому потрібен `/lib/libc.so` для запуску програм. Йому потрібен `/etc/passwd`.
Ця колекція файлів називається **Userland** (або Базова Система).

**Як створити "Золотий Образ" (Ручний метод):**
Ми не хочемо розпаковувати файли кожного разу, коли створюємо jail. Ми робимо це *один раз*, щоб створити майстер-шаблон.

```bash
# 1. Створити набір даних для нашого Золотого Образу
zfs create -o mountpoint=/usr/jails/base-13.2 zroot/jails/base-13.2

# 2. Завантажити офіційний FreeBSD Userland (base.txz)
fetch https://download.freebsd.org/ftp/releases/amd64/13.2-RELEASE/base.txz

# 3. Розпакувати його в набір даних
tar -xf base.txz -C /usr/jails/base-13.2

# 4. Заблокувати його (Знімок/Snapshot)
zfs snapshot zroot/jails/base-13.2@gold

```

Тепер у нас є чиста копія операційної системи "тільки для читання".

### 1.2 Суперсила ZFS: Клони проти Tarballs

Ось де FreeBSD залишає Linux позаду. Щоб створити новий jail, ми не копіюємо ці файли. Ми **Клонуємо** їх.

```bash
# Створити новий jail зі знімка
zfs clone zroot/jails/base-13.2@gold zroot/jails/web01

```

**Чому це важливо для Архітектора:**

* **Швидкість:** Клон створюється за мілісекунди.
* **Ефективність:** Він споживає **нуль байт** сховища, поки ви не запишете дані. Він вказує на оригінальні блоки.
* **Безпека:** Перед ризикованим оновленням, `zfs snapshot zroot/jails/web01@pre-upgrade`. Якщо воно зламається, `zfs rollback` миттєвий.

### 1.3 Реалізація

Тепер, коли у нас є файлова система, ми налаштовуємо клітку.

**1. Підготовка Мережі Хоста (Міст)**
Нам потрібен віртуальний комутатор. Оскільки ми хочемо використовувати приватні IP (NAT), ми даємо мосту IP шлюзу.

```bash
ifconfig bridge0 create
ifconfig bridge0 10.0.0.1/24 up

```

**2. Налаштування Jail (`/etc/jail.conf`)**
Ми використовуємо VNET (VIMAGE), щоб дати jail власний мережевий стек.

```text
web01 {
    path = "/zroot/jails/web01";
    vnet;
    vnet.interface = "epair0b";

    # Створити кабель, увімкнути в міст
    exec.prestart += "ifconfig epair0 create up";
    exec.prestart += "ifconfig bridge0 addm epair0a";

    # Налаштувати IP всередині jail
    exec.start += "/sbin/ifconfig epair0b 10.0.0.2/24 up";
    exec.start += "/sbin/route add default 10.0.0.1";
    exec.start += "/bin/sh /etc/rc";

    # Очищення
    exec.poststop += "ifconfig bridge0 deletem epair0a";
    exec.poststop += "ifconfig epair0a destroy";
}

```

**3. Запуск Звіра**

```bash
service jail start web01
jexec web01 /bin/sh

```

Всередині запустіть `pkg install apache24`. З хоста це просто процес. Зсередини — це сервер.



## 2. Підхід Linux: Namespaces та Cgroups

Переходячи до Linux, все стає складнішим, але більш гранулярним.
На відміну від FreeBSD, "Контейнерів" не існує в ядрі Linux. Немає системного виклику з назвою `create_container()`.

Натомість ми використовуємо дві окремі технології, склеєні разом:

1. **Namespaces (Простори імен):** Ізолюють *видимість* (Що я можу бачити).
2. **Cgroups (Контрольні групи):** Ізолюють *ресурси* (Що я можу використовувати).

### 2.1 Створення з Нуля (Важкий Шлях)

У FreeBSD ми використовували `fetch` та `tar`. У Linux ми використовуємо `debootstrap` (для Debian/Ubuntu) або розпаковуємо tarball з rootfs (Alpine).

Якщо б ви хотіли створити контейнер **без** Docker або LXC, ви б зробили це так:

```bash
# 1. Завантажити і розпакувати мінімальну систему Debian
sudo debootstrap --variant=minbase stable /var/lib/containers/web01 http://deb.debian.org/debian

# 2. Ізолювати його (Ручний вхід у chroot/namespace)
sudo unshare --fork --pid --mount --net chroot /var/lib/containers/web01 /bin/bash

```
Це створю ізоляцію, але без cgroups або правильного init — це навчальний приклад.

Ця команда `debootstrap` є Linux-еквівалентом розпакування `base.txz`. Вона стягує `apt`, `bash` та `coreutils`, щоб створити робоче середовище.

### 2.2 "Легкий" Шлях (LXC)

Інструменти на зразок **LXC** автоматизують це. Коли ви запускаєте `lxc launch`, він завантажує попередньо зібраний образ (результат запуску `debootstrap`) і розпаковує його для вас.

```bash
# Завантажує образ і створює контейнер
lxc launch ubuntu:22.04 web01

# Вхід у контейнер
lxc exec web01 -- bash

```

### 2.3 Прихована Небезпека: Квоти CPU та Багатопотоковість

Ось де багато хто зазнає невдачі.
Коли ви встановлюєте ліміт "1 CPU" на контейнер, ви кажете **CFS (Completely Fair Scheduler)** давати цьому контейнеру 100мс часу виконання кожні 100мс вікна.

**Сценарій A: Node.js Додаток (Однопотоковий)**
Node.js працює інтенсивно, досягає ліміту 100мс, ставиться на паузу і відновлюється. Він сповільнюється, але працює.

**Сценарій B: Java/JVM Додаток (Багатопотоковий)**
JVM створює 8 потоків. Якщо всі вони прокидаються одночасно, вони спалюють вашу квоту "1 CPU" за **12.5 мілісекунд**.
Ядро дроселює контейнер на решту 87.5мс. Ваш додаток зависає, спричиняючи масивні стрибки затримок.
**Урок Архітектора:** Узгоджуйте ліміти контейнерів з моделлю потоків вашого додатку.



## 3. Мережа: Віртуальні Кабелі та Мости

Як ці клітки розмовляють зі світом? Це не магія; це комутація 2-го рівня (Layer 2).
Ми використовуємо пари **Virtual Ethernet (veth)** або **epairs**. Уявіть їх як віртуальний патч-кабель:

* **Кінець A** встромлений у Контейнер.
* **Кінець B** встромлений у віртуальний комутатор (Міст) на Хості.

### FreeBSD: Міст та Epair

У FreeBSD ми створюємо міст (`bridge0`), який діє як Шлюз. Jail отримує інтерфейс `epair`.
Оскільки Jail має приватну IP (`10.0.0.2`), ми використовуємо **PF** для NAT:

```text
# /etc/pf.conf
jail_net="10.0.0.0/24"
nat on em0 from $jail_net to any -> (em0)
rdr on em0 proto tcp from any to any port 80 -> 10.0.0.2

```

### Linux: Міст Linux

LXC/Docker створює `br0`. Коли контейнер запускається, він створює пару `veth`. Один кінець залишається на хості (`veth123`), інший переміщується в простір імен контейнера (`eth0`).



## 4. Файлові Системи: Пастка Продуктивності

Нарешті, зберігання. Це місце, де архітектурна розбіжність є найбільш болючою.

### Проблема Linux: Накладні Витрати OverlayFS

Більшість Linux контейнерів використовують **OverlayFS**. Вона накладає образ "тільки для читання" і верхній шар для запису.
**Пастка:** Якщо ви змінюєте файл розміром 1ГБ, ядро повинно **скопіювати весь 1ГБ файл** з нижнього шару на верхній перед записом жодного байта. Ця затримка "Copy-Up" вбиває продуктивність баз даних.

### Рішення FreeBSD: Набори Даних ZFS (Datasets)

FreeBSD Jails не потребують OverlayFS, тому що ZFS обробляє CoW на **рівні блоків**.
Зміна одного байта файлу розміром 1ГБ виділяє один новий блок. Немає масивного копіювання файлу.

### Універсальне Правило: Дані Втікають

Незалежно від ОС, тимчасові контейнери не повинні зберігати постійні дані. Ми пробиваємо дірку крізь стіну контейнера.

* **FreeBSD (Nullfs):**
```bash
mount_nullfs /data/mysql /usr/jails/db01/var/db/mysql

```

* **Linux (Bind Mount):**
```bash
lxc config device add db01 mysqldata disk source=/data/mysql path=/var/lib/mysql

```

Тепер "мозок" (MySQL) знаходиться в клітці, але "пам'ять" (Дані) сидить безпечно на хості.
