# Безпека як код: AI Landing Zone — фундамент під кожним агентом на GCP

> **«Кожен розгорнутий агент успадковує фундамент, на який він стає. Захистити одного агента можна за один спринт. Але неможливо перебудувати й зміцнити фундамент, коли на ньому вже працює сотня агентів».**

Протягом останніх місяців у цій серії ми рухалися від верхівки агентного стека до самого низу. Трилогія **«Безпека AI-агентів»** чітко окреслила головні загрози: [промпт-ін'єкції](#agent-security-part1), [сліпу довіру між агентами](#agent-security-part2) та [отруєння ваг моделей](#agent-security-part3). [Оцінка безпеки платформи AI-агентів](#agent-platform-security-assessment) перетворила їх на сімнадцять перевірок, які можна оцінити кількісно. Стаття про [AI Gateway](#ai-gateway-enforcement) показала, як перевести ці перевірки зі статусу *Документовано* у статус *Примусово (Enforced)* безпосередньо на шляху проходження трафіку. А матеріал [«Власна розробка чи готове рішення»](#build-vs-buy-agent-platforms-gcp) допоміг обрати середовище для їх запуску.

Усі чотири статті мовчазно припускали одне: що під агентами вже існує організація Google Cloud, де політики, мережа, керування ключами та доступи (IAM) спроєктовані спеціально під них. У більшості організацій, які я бачив, цього немає. Їхня landing zone була спроєктована у 2021 році для вебзастосунків і конвеєрів обробки даних, а агентів розгортають туди так, ніби це просто ще один вебсервіс.

Ця стаття описує цей відсутній рівень: **AI landing zone**. Вона базується на архітектурному та управлінському шаблоні (blueprint), який я розробляв саме для цього завдання — Gemini Enterprise, середовища виконання Agent Platform, власні MCP-сервери та мультиагентні системи на GCP — і звірена з актуальною документацією Google станом на жовтень 2026 року.

Резюме для керівництва нижче призначене для тих, хто погоджує бюджети й приймає ризики. Розділи з 1 по 11 — для інженерів, які будують платформу.

## Резюме для керівництва: бізнес-обґрунтування фундаменту

**Прірва між пілотом і продакшеном.** Звіт Cisco *Agent Trust Gap* (березень 2026 р.) виявив разючу асиметрію: 85% організацій експериментують з AI-агентами, пілотують або розгортають їх, але лише 5% вивели їх у повноцінний продакшен. Майже 60% керівників служб безпеки назвали питання безпеки головною перешкодою для ширшого впровадження. У Gartner Hype Cycle for AI Governance (2026 р.) позиції *agentic AI governance* та *AI agent identity* розташовані на відстані двох-п'яти років від масового впровадження на ринку.

У більшості випадків пілоти працюють. Бракує надійної базової інфраструктури, спираючись на яку служба безпеки могла б погодити вихід у продакшен.

**Чому агентів важко погоджувати.** Традиційне ПЗ працює за сценаріями, які розробники заздалегідь написали та перевірили на код-рев'ю. Натомість агент обирає наступну дію динамічно в рантаймі, діючи від імені наданих йому облікових даних і спираючись на зовнішній текст, якого ви не писали: знайдений у базі знань документ, тікет підтримки чи відповідь зовнішнього інструмента. Керівник служби безпеки не може погодити таку систему лише на основі системного промпту чи регламенту у вікі. Дозвіл можливий лише тоді, коли найгірші сценарії заблоковані самою платформою — незалежно від того, як поведеться окремий агент.

### Що забезпечує AI landing zone

| Проблема | Що робить landing zone | Що отримує керівництво |
|---|---|---|
| **Погодження в масштабі** | Служба безпеки погоджує платформу один раз; нові агенти автоматично успадковують її механізми захисту | Кожен новий агент проходить автоматичну перевірку в CI-пайплайні замість індивідуального кількамісячного аудиту безпеки |
| **Радіус ураження** | Агенти, інструменти та дані ізольовані в окремих проєктах; доступ надається до конкретного датасету, а не до всього проєкту | Скомпрометований агент має доступ лише до виділених йому даних, а не до всієї інфраструктури компанії |
| **Резидентність даних і контроль ключів** | Зберігання даних обмежене затвердженими регіонами (у цьому шаблоні — ЄС); ключі шифрування під контролем клієнта (CMEK) належать службі безпеки | Підтверджені аудитом докази виконання вимог GDPR та зобов'язань щодо локалізації даних |
| **Підзвітність** | Індивідуальна IAM-ідентичність для кожного агента замість спільних сервісних акаунтів | Дії в журналі аудиту однозначно відстежуються до конкретного агента, а не до загального облікового запису |
| **Докази замість запевнень** | Кожне обмеження перевіряється негативним тестом, який блокує збірку, якщо захист не спрацював | Аудитори та комітети з ризиків перевіряють результати автотестів, а не запевнення на слайдах презентацій |
| **Стримування витрат** | Індивідуальні ліміти токенів для агентів на рівні шлюзу; бюджети зі spend-cap на рівні проєкту як аварійний запобіжник | Зациклений чи атакований запитами агент впирається в жорсткий ліміт, а не спустошує місячний бюджет |

**Ціна відсутності фундаменту.** Без спільної основи кожна команда будує власні механізми захисту на власний розсуд. Перевірка безпеки стає вузьким місцем для кожного релізу, тіньові MCP-сервери з'являються в проєктах, за якими ніхто не стежить, а ризики неконтрольовано накопичуються. Landing zone переносить рішення щодо безпеки з рівня окремого агента на рівень платформи, де воно приймається один раз і перевіряється безперервно.

**Вартість володіння.** Утримання платформи має постійну ціну, і більша частина цих витрат є фіксованою. Наприклад, Secure Web Proxy коштує $1.25 за годину роботи шлюзу — близько $910 на місяць за кожен постійно активний екземпляр без урахування обробки трафіку та сертифікатів інспекції TLS. Порівнюйте цю суму з втратами від одного заблокованого релізу в продакшен, а не з нулем. Витрати на моделі також потребують верхньої межі, і цей захист має бути дворівневим. Стандартний бюджет у Cloud Billing лише надсилає сповіщення. Бюджет із жорстким лімітом (spend-cap) може примусово вимкнути Agent Platform API для всього проєкту, проте це відбувається із затримкою і зупиняє одразу всіх агентів у проєкті. Це радше аварійний стоп-кран, ніж інструмент точного контролю. Точне обмеження діє безпосередньо на шляху проходження трафіку — як індивідуальний ліміт токенів для кожного агента, що контролюється на рівні шлюзу.

**Регулювання.** Для європейських організацій ця ж доказова база закриває вимоги EU AI Act. Підтвердження людиною викликів інструментів, що змінюють стан (state-changing tools), захищені від модифікації логи рішень агентів та збережені результати тестів відповідають вимогам Закону щодо ведення записів (Стаття 12), нагляду з боку людини (Стаття 14) та моніторингу після виходу на ринок (Стаття 72). Сама по собі landing zone не робить систему автоматично комплаєнтною — класифікація та оцінка відповідності є юридичними процедурами. Проте вона генерує технічні докази, яких вимагають ці процеси. З огляду на те, що пакет поправок Digital Omnibus щодо ШІ набув чинності 27 липня 2026 року, вимоги до систем високого ризику почнуть діяти з 2 грудня 2027 року (Додаток III) та 2 серпня 2028 року (Додаток I). Цього часу достатньо, щоб збудувати надійний фундамент, але замало, щоб відкладати старт.

**Хто цим керує.** Фундамент потребує постійної експлуатації, а не лише одноразового розгортання. Команда Platform Engineering будує та підтримує його; Information Security затверджує кожне захисне обмеження (guardrail) і кожен виняток; Network Engineering відповідає за мережеві периметри та правила вихідного трафіку (egress); відповідальний за IAM керує обліковими записами агентів. Онбординг нових агентів автоматизовано в CI, а час інженерів витрачається за фіксованим розкладом: щотижневий аналіз заблокованих запитів і відмов у доступі, щомісячний перегляд життєвого циклу моделей і реєстру винятків, щоквартальна ресертифікація прав і навчання red-team. Це чітко закріплені обов'язки в межах існуючих команд, а не привід створювати новий департамент. Якщо ці завдання не внесені до чиїхось цілей (OKR), білий список моделей і реєстр винятків застаріють уже за квартал.

**Поетапне розгортання через контрольні гейти, а не за датами в календарі.** Захисні механізми впроваджуються у сім фаз, кожна з яких завершується перевіркою критеріїв виходу та підписами керівників Security і Platform (розділ 9). Кожне обмеження спочатку запускається в режимі dry-run, тому невідповідності в існуючих сервісах виявляються у звітах, а не призводять до збоїв у роботі.

## 1. Чому ваша поточна landing zone не покриває агентів

Традиційна landing zone — чи то шаблон Google Security Foundations, Cloud Foundation Fabric FAST, чи ваша власна реалізація — чудово вирішує завдання 2021 року: ієрархія ресурсів, Shared VPC, централізоване логування, відсутність публічних IP-адрес, жодних дефолтних сервісних акаунтів. Залиште все це. Це надійна основа, на якій будується архітектура цієї статті.

Чого вона не враховує — це чотирьох фундаментальних властивостей, якими агенти відрізняються від класичних робочих навантажень:

1. **Інструкції та дані передаються одним каналом.** Модель не здатна надійно відрізнити ваш системний промпт від інструкцій, прихованих у тексті завантаженого тікета підтримки. Жоден мережевий екран не бачить цієї різниці. (OWASP ASI01, Agent Goal Hijack — тема [Частини 1](#agent-security-part1).)
2. **IAM перевіряє повноваження, а не наміри.** IAM відповідає на запитання: *«чи має цей принципал право читати цю таблицю?»*. Він не може відповісти: *«чи повинен він робити це просто зараз лише тому, що так написано в прочитаному документі?»*. Агент із загальним сервісним акаунтом реалізує класичну вразливість *confused deputy* («обдурений посередник»), отримуючи ключі до всього, до чого має доступ цей акаунт. (ASI02, Tool Misuse.)
3. **Контрагент за замовчуванням не верифікований.** Картки агентів (agent cards) заповнюються самими розробниками; MCP-сервери завантажуються з інтернету; текстові описи інструментів фактично стають інструкціями до виконання. (ASI04, ASI07 — [Частина 2](#agent-security-part2).)
4. **Самі дані (payload) можуть стати зброєю.** Сканери контейнерів знаходять CVE у бінарних файлах. Але вони не виявлять бекдор, зашитий у ваги моделі, чи отруєний документ у базі знань RAG. (ASI04, ASI06 — [Частина 3](#agent-security-part3).)

Жодна з цих проблем не вирішується всередині самого агента. Проте всі чотири можна *локалізувати й стримати* силами платформи, на якій цей агент працює. Це і є головний принцип проєктування всього, що описано далі:

```text
Захисні бар'єри (guardrails) живуть на рівні платформи, а не в промпті.
Якщо скомпрометований агент може обійти перевірку — це побажання, а не механізм захисту.
```

## 2. Архітектурний каркас: чотири рівні, один напрямок довіри

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ ОРГАНІЗАЦІЯ       org policies: без SA keys, invoker IAM, CMEK, EU-only, │
│                   кастомні MCP-конектори заблоковані за замовчуванням    │
├──────────────────────────────────────────────────────────────────────────┤
│ ПАПКИ             fldr-shared-infra │ fldr-ai-platform │ fldr-ai-workloads│
│                   (net, KMS, logs)  │ (registry, Gemini│  sandbox → dev → │
│                                     │  Enterprise hub) │  staging → prod  │
├──────────────────────────────────────────────────────────────────────────┤
│ МЕРЕЖА            периметри VPC-SC · PSC-I у Shared VPC ·                 │
│                   Secure Web Proxy для всього egress · без інтернету     │
├──────────────────────────────────────────────────────────────────────────┤
│ РАНТАЙМ           IAM-ідентичність · Agent Gateway + Model Armor ·        │
│                   Agent Registry · Binary Authorization                  │
└──────────────────────────────────────────────────────────────────────────┘
        Кожен наступний рівень проєктується з припущенням, що попередній уже пробито.
```

Послідовність має вирішальне значення. Організаційні політики — це єдиний запобіжник, який спрацює, навіть якщо власник проєкту припуститься помилки. Мережевий рівень стримує атаку, коли викрадено облікові дані. Рівень рантайму захищає тоді, коли мережеве з'єднання легітимне, але сам переданий контент є шкідливим. Ешелонована оборона (defense in depth) тут не просто гасло, а порядок зведення всієї конструкції.

## 3. Ієрархія: радіус ураження визначається структурою папок

Ієрархія ресурсів — це рівень, де ви один раз і без додаткових витрат визначаєте межі того, що може бути скомпрометовано одночасно.

```text
organizations/ORG_ID
├── fldr-shared-infra
│   ├── prj-net-host-prod        Shared VPC, мережеві підключення PSC, Secure Web Proxy
│   ├── prj-sec-kms-prod         усі ключі CMEK, Certificate Authority Service
│   └── prj-sec-logging          замкнені (locked) бакети логів, SIEM-експортери
├── fldr-ai-platform
│   ├── prj-ai-registry-shared   Agent Registry, підписаний Artifact Registry
│   └── prj-gemini-ent-hub       застосунки Gemini Enterprise, сховища даних, конектори
└── fldr-ai-workloads
    ├── fldr-ai-sandbox          експерименти з відкритими вагами, ізольована VPC, без прод-даних
    ├── fldr-ai-dev              синтетичні дані
    ├── fldr-ai-staging          дзеркало прод-allowlist, перевірка регресій безпеки
    └── fldr-ai-prod
        ├── prj-agent-runtime-prod   рантайм Agent Platform / оркестратори
        ├── prj-mcp-servers-prod     MCP-інструменти, які викликають агенти (тільки internal ingress)
        ├── prj-mcp-gemini-prod      MCP-інструменти для Gemini Enterprise (єдиний виняток для ingress)
        └── prj-ai-data-prod         Vector Search, датасети BigQuery, бакети з даними для grounding
```

Чотири рішення в цьому дереві несуть основне архітектурне навантаження:

- **Агенти, інструменти та дані рознесені у три різні проєкти, а не зібрані в одному.** Обліковий запис рантайму читає дані через точкові прив'язки прав на рівні окремих датасетів і бакетів; він ніколи не отримує ролей доступу до даних на рівні всього проєкту. Якщо агента зламають, зловмисник отримає лише вузький, чітко окреслений перелік дозволів.
- **Gemini Enterprise виділено у власний хаб-проєкт.** Як показано в розділі 5, підключення власних інструментів вимагає *послаблення* загальноорганізаційної політики. Таке послаблення має існувати рівно в одному місці в межах організації та бути оточеним компенсувальними заходами безпеки.
- **Інструменти, які викликає Gemini Enterprise, відокремлені від інструментів, які викликають агенти.** Gemini Enterprise звертається до MCP-серверів із зовнішньої щодо вашої VPC мережі Google, що змушує робити виняток для вхідного трафіку (розділ 5). Ізоляція цих сервісів в окремому проєкті дозволяє не поширювати цей виняток на решту інструментів і залишити `prj-mcp-servers-prod` під повним захистом периметра.
- **Ключі шифрування та логи належать команді Security, а не платформеній команді.** Інженери, які мають права розгортати агента, не повинні мати технічної можливості видалити аудит-лог його дій або знищити криптографічний ключ, яким зашифровані його дані. Це принцип розділення обов'язків (segregation of duties), реалізований через межі проєктів.

## 4. Організаційні політики: обмеження, які неможливо обійти

Організаційні політики не потребують витрат на обслуговування, і жоден власник проєкту не може їх вимкнути. Наш шаблон використовує 34 обмеження (constraints) на трьох рівнях ієрархії; найважливіші з них для інфраструктури агентів наведено нижче.

| Обмеження (Constraint) | Рівень | Що воно унеможливлює |
|---|---|---|
| `iam.managed.disableServiceAccountKeyCreation` / `…KeyUpload` | Org | Довгострокові JSON-ключі — головна мішень зловмисників для викрадення та ексфільтрації даних |
| `run.managed.requireInvokerIam` | Org | Неавтентифіковані (`allUsers`) сервіси Cloud Run — кожен MCP-інструмент вимагає підтвердженої IAM-ідентичності для виклику |
| `run.managed.disableInlinedSource` | Org | Розгортання напряму з вихідного коду в обхід перевіреного та відсканованого образу в реєстрі |
| `discoveryengine.managed.disableCustomMcpServerConnector` | Org | Тіньові конектори MCP у Gemini Enterprise (увімкнено Google за замовчуванням) |
| `gcp.restrictNonCmekServices` + `gcp.restrictCmekCryptoKeyProjects` | Org | Незашифровані ресурси AI, сховищ, баз даних і секретів; зберігання ключів поза межами проєкту безпеки |
| `gcp.resourceLocations` | Org | Зберігання даних за межами юрисдикції ЄС |
| `vertexai.allowedModels` | Prod folder | Виклик, донавчання (tuning) або розгортання будь-якої моделі поза затвердженим білим списком |
| `vertexai.genAIGroundingSources` + `disableGenAIGoogleSearchGrounding` | Prod folder | Прив'язка (grounding) відповідей у продакшені до результатів пошуку у відкритому інтернеті |
| `run.allowedBinaryAuthorizationPolicies` = `default` | Workloads folder | Запуск сервісів Cloud Run без криптографічного підпису Binary Authorization |
| `run.allowedIngress` = `internal…` | Workloads folder | Доступність агентів та інструментів із публічного інтернету (за одним задокументованим винятком — див. §5) |

Два правила дозволяють впровадити ці обмеження в живій компанії без простоїв.

**Спочатку завжди dry-run.** Кожне обмеження спершу розгортається в блоці `dryRunSpec`. Порушення в логах аналізуються протягом узгодженого вікна, і лише після усунення невідповідностей правило переводиться в бойовий режим `spec`:

```yaml
# Етап 1: логувати порушення, нічого не блокувати
name: organizations/ORG_ID/policies/run.managed.requireInvokerIam
dryRunSpec:
  rules:
  - enforce: true
---
# Етап 2: після завершення періоду перевірки те саме правило переводиться в режим блокування
name: organizations/ORG_ID/policies/run.managed.requireInvokerIam
spec:
  rules:
  - enforce: true
```

**Кожне обмеження супроводжується негативним тестом.** Статус «Примусово (Enforced)» означає, що ви спробували виконати заборонену дію (створити ключ сервісного акаунта, розгорнути публічний сервіс, викликати недозволену модель), і платформа заблокувала запит. Саме ця відмова, зафіксована в логах CI-пайплайну, є доказом для аудиту. Скриншот сторінки налаштувань у консолі таким доказом не є.

### Білий список моделей — це процес, а не статичний конфіг

`vertexai.allowedModels` — це обмеження, суть якого керівництво схоплює найшвидше (*«продакшен може викликати лише моделі, погоджені службою безпеки»*), і на якому інженерні команди найчастіше спотикаються, оскільки статичний список миттєво застаріває.

Згадайте події останніх дванадцяти тижнів. Згідно з офіційним графіком життєвого циклу Google, підтримка Gemini 2.5 Pro, Flash та Flash-Lite на Vertex AI та Agent Platform офіційно припиняється **20 жовтня 2026 року** (сьогодні). За цей самий час у реліз-ноутках платформи зафіксовано вихід Gemini 3.6 Flash і 3.5 Flash-Lite (21 липня), 3.7 Flash (13 серпня), 3.8 Flash (2 вересня) та Gemini 4 Argon (13 жовтня) — при цьому для Gemini 3.6 Flash виведення з експлуатації призначено вже на наступний місяць (19 листопада 2026 року). Білий список, сформований у липні, наприкінці жовтня застаріє двічі: він досі дозволятиме моделі, які вимикаються просто сьогодні, і блокуватиме нові GA-моделі, на які прагнуть перейти команди.

Тому правила ведення allowlist мають описувати життєвий цикл, а не просто фіксувати ідентифікатори:

```yaml
# folders/PROD_AI_FOLDER_ID — ілюстративний приклад; точні ID оновлюються під час щомісячного перегляду
name: folders/PROD_AI_FOLDER_ID/policies/vertexai.allowedModels
spec:
  rules:
  - values:
      allowedValues:
      - publishers/google/models/<GA_FLASH_MODEL_ID>:predict
      - publishers/google/models/<GA_EMBEDDING_MODEL_ID>:predict
      - publishers/anthropic/models/<APPROVED_PARTNER_MODEL_ID>:predict
```

- У продакшені дозволено **виключно дію `:predict`** — жодного `:tune` і жодного розгортання в один клік через `:deploy`.
- **Лише GA-версії моделей** — жодних `-preview` чи динамічних аліасів `-latest`. Динамічний аліас означає неконтрольовану зміну моделі просто в продакшені.
- Нова версія моделі спочатку додається **у staging**, проходить там набір тестів на регресію безпеки і лише після цього переноситься у продакшен.
- Список переглядається **щомісяця** відповідно до офіційного графіка життєвого циклу моделей із чітким KPI: *нуль робочих навантажень у продакшені на моделях, до виведення яких з експлуатації залишилося менше ніж 30 днів.*
- Для моделей від партнерів необхідно додатково налаштувати друге обмеження — `vertexai.allowedPartnerModelFeatures`, інакше такі функції, як структурований вивід (structured outputs), не працюватимуть. Дозволити саму лише модель недостатньо.

## 5. Пастка інтеграції Gemini Enterprise та кастомних MCP

Цей розділ варто перечитати двічі кожній платформеній команді. Саме тут правильно спроєктована landing zone лоб у лоб стикається з бізнес-вимогами, а необхідна документація Google розпорошена по п'яти різних розділах.

Бізнес-вимога звучить так: *«Надайте співробітникам можливість через Gemini Enterprise робити запити й виконувати дії у внутрішніх корпоративних системах за допомогою наших власних MCP-серверів»*. Правильно налаштована landing zone за замовчуванням блокує кожну ланку цього ланцюжка.

### Три політики, які працюють лише у зв'язці

Кастомні MCP-конектори за замовчуванням заблоковані керованим обмеженням Google. Щоб дозволити їх у хаб-проєкті, потрібно одночасно сконфігурувати **три** політики — послабити одну та посилити дві інші:

```yaml
# 1. Послабити: дозволити custom MCP — виключно в цьому єдиному проєкті
name: projects/PRJ_GEMINI_HUB/policies/discoveryengine.managed.disableCustomMcpServerConnector
spec:
  rules:
  - enforce: false
---
# 2. Посилити: визначити вичерпний перелік дозволених типів конекторів
name: projects/PRJ_GEMINI_HUB/policies/discoveryengine.managed.allowedDataSources
spec:
  rules:
  - enforce: true
    parameters:
      allowedDataSources: [custom_mcp, sharepoint, jira, servicenow]
      enforcedProjects: [projects/PRJ_GEMINI_HUB_NUMBER]
---
# 3. Посилити: вказати точні хости, до яких конектори мають право звертатися
name: projects/PRJ_GEMINI_HUB/policies/discoveryengine.managed.allowedEgressFqdns
spec:
  rules:
  - enforce: true
    parameters:
      allowedEgressFqdns:
      - mcp-orders-PRJ_MCP_GEMINI_NUMBER.europe-west4.run.app   # MCP-сервер для Gemini
      - auth.corp.example.com                                  # авторизація OAuth
      - token.corp.example.com                                 # отримання токенів OAuth
      enforcedProjects: [projects/PRJ_GEMINI_HUB_NUMBER]
```

Важливий нюанс: дві обмежувальні політики (п. 2 і 3) спрацьовують лише для тих проєктів, які або входять до периметра VPC Service Controls, або явно перелічені в параметрі `enforcedProjects`. Якщо жодна з цих умов не виконана, вимкнення першого обмеження просто відчиняє двері навстіж без жодних фільтрів. Саме тому хаб-проєкт одночасно і включений у продакшен-периметр, і явно прописаний у списку `enforcedProjects`.

### Мережевий трафік іде зовсім не тим шляхом, який ви малювали на схемі

Gemini Enterprise викликає ваш MCP-сервер **із керованої інфраструктури Google, а не з вашої Shared VPC**. Це призводить до трьох неочевидних наслідків:

1. **Ваша політика `run.allowedIngress = internal` заблокує цей виклик.** Для проєкту, де працюють ці сервіси, потрібен точковий оверрайд політики на рівень `all`. Саме тому їх винесено в окремий проєкт `prj-mcp-gemini-prod`: усі інші інструменти, до яких звертаються лише агенти, залишаються в `prj-mcp-servers-prod`, де вимога `internal` ніколи не послаблюється.
2. **Ендпоінт повинен мати публічне доменне ім'я та сертифікат від публічного центру сертифікації (CA).** Самопідписані сертифікати відхиляються, а внутрішні адреси `*.internal` є недосяжними. Приватні DNS-імена чудово працюють для трафіку між агентами й інструментами всередині VPC, але для викликів із Gemini Enterprise вони не підійдуть.
3. **Використовуйте стандартний URL `*.run.app`, а не власний домен.** Gemini Enterprise передає підписаний Google ID-токен у заголовку `X-Serverless-Authorization` (паралельно з користувацьким OAuth-токеном у заголовку `Authorization`), але робить це *виключно* під час звернення до стандартних доменів `run.app`. Якщо ви поставите перед сервісом власний домен `mcp.corp.example.com`, ID-токен безслідно зникне, а разом із ним перестане працювати й перевірка IAM на рівні Cloud Run.

**І це неможливо обійти за допомогою правила вхідного трафіку (ingress rule) у VPC Service Controls.** Саме на цьому місці сиплеться більшість архітектурних рішень. Під час викликів Cloud Run механізм VPC-SC не перевіряє IAM-ідентичність ініціатора запиту, тому правила ingress із прив'язкою до конкретного принципала (наприклад, сервісного агента Discovery Engine) тут не підтримуються — дозволено лише значення `ANY_IDENTITY`. Таким чином, сервіс із налаштуванням вхідного трафіку `all` на рівні виклику взагалі не захищений периметром. На архітектурному рев'ю варто прямо зафіксувати: для вхідних викликів сервіси, до яких звертається Gemini, лежать поза захистом периметра VPC-SC, і їхня безпека тримається виключно на компенсувальних механізмах нижче. Це прийнятно лише тому, що вони ізольовані в окремому проєкті, зведені до мінімуму та оформлені як контрольований виняток.

Усі перелічені нижче компенсувальні заходи є суворо обов'язковими:

- політика `run.managed.requireInvokerIam` залишається активною: жодних `allUsers` за жодних обставин;
- роль `roles/run.invoker` надається виключно сервісному агенту Discovery Engine та конкретним IAM-ідентичностям агентів;
- URL сервісу явно прописаний у білому списку `allowedEgressFqdns`;
- кожен виклик інструмента проходить перевірку через Model Armor;
- виняток зафіксовано в реєстрі з приміткою про перегляд архітектури, щойно Google реалізує підтримку приватного мережевого маршруту.

### Підтвердження людиною можна випадково вимкнути однією анотацією в коді

Gemini Enterprise за замовчуванням трактує кожен MCP-інструмент як потенційно небезпечний: після імпорту інструменти перебувають у **вимкненому** стані, а кожен їх виклик вимагає явного підтвердження від користувача в інтерфейсі. Розробники можуть прибрати це вікно підтвердження для інструментів, які працюють лише на читання:

```python
@mcp.tool(annotations={"readOnlyHint": True, "destructiveHint": False})
def query_order_status(order_id: str) -> dict:
    """Read-only перевірка статусу замовлення."""
    return db.fetch_order(order_id)
```

Це логічний і потрібний механізм, адже втома від постійних спливаючих вікон (confirmation fatigue) сама по собі створює ризик безпеки. Але зверніть увагу, хто саме цим керує: **розробник інструмента** безпосередньо в коді за допомогою одного булевого прапорця. Якщо розробник помилково або свідомо вкаже `readOnlyHint: True` для інструмента, що змінює дані, підтвердження користувачем зникне — і служба безпеки про це навіть не дізнається.

Саме тому наша landing zone вводить додатковий механізм захисту, якого ще не було в попередньому чеклісті оцінювання — я пропоную додати його як вісімнадцяту перевірку. Оскільки анотація в коді може бути хибною, система захисту не покладається лише на неї:

```text
R7 (Reach) — Інструменти, що змінюють стан, вимагають підтвердження людиною,
             а read-only інструменти технічно позбавлені прав на запис.   OWASP ASI09
Вважається примусово забезпеченим (Enforced), коли:
1. CI-пайплайн блокує будь-який MCP-інструмент без readOnlyHint: true, якщо він
   явно не декларує destructiveHint: true.
2. Будь-яка зміна значення readOnlyHint вимагає повторного погодження в Agent Registry.
3. Інструменти для читання (read-only) та запису (write) розгортаються як окремі
   MCP-сервіси з різними IAM-ідентичностями. Обліковий запис read-only сервісу має
   виключно ролі читача в БД, тому навіть неправильно проанотований інструмент
   отримає помилку доступу на рівні сховища даних.
4. Тести red-team підтверджують, що кожен інструмент із правами запису запитує дозвіл у користувача.
```

У сценаріях, де Gemini Enterprise прокидає OAuth-токен кінцевого користувача, цільова система додатково перевіряє повноваження самої людини. Обліковий запис інструмента виступає тут другим рубежем оборони, а не єдиним.

## 6. Мережа: периметри, приватні маршрути та інспекція вихідного трафіку (egress)

Завдання мережевого рівня формулюється в одному реченні: **жоден агент не повинен мати доступу до інтернету або даних іншого проєкту маршрутом, який не інспектується.**

```text
Рантайм Agent Platform (Google tenant project)
        │  інтерфейс PSC — виключно приватний трафік RFC 1918
        ▼
Shared VPC (prj-net-host-prod)
    ├── внутрішні MCP-інструменти (Cloud Run --ingress=internal, GKE default-deny NetworkPolicy)
    └── Secure Web Proxy ── білий список FQDN, інспекція TLS
              └── Cloud NAT ── доступ лише до затверджених зовнішніх API
```

**VPC Service Controls** обгортає всі AI API — `aiplatform`, `discoveryengine`, `modelarmor`, сховища даних, BigQuery, AlloyDB, Cloud SQL, Cloud Run, Artifact Registry, Secret Manager, KMS — у три окремі периметри: sandbox, non-production та production. Правила обміну даними між периметрами містять виключно конкретні ідентичності та методи — жодних шаблонів `*`. IAM-ідентичності агентів можна вказувати безпосередньо як принципалів у правилах ingress та egress (як для окремого агента, так і для всього флоту через `principalSet://…/attribute.…`), хоча в рівнях доступу (access levels) вони наразі не підтримуються.

**Інтерфейси Private Service Connect (PSC-I)** підключають керований рантайм до вашої VPC для маршрутизації приватного трафіку. Проте самі по собі вони не обмежують вихід рантайму в публічний інтернет. Поза межами периметра VPC-SC рантайм Agent Platform зберігає прямий доступ до інтернету, і цей трафік виходить назовні безпосередньо з тенант-мережі Google. Він узагалі не заходить у вашу VPC, оминаючи ваші файрволи та проксі-сервери. Цей обхідний шлях перекривається саме за допомогою VPC Service Controls: щойно проєкт рантайму опиняється всередині периметра, стандартний інтернет-канал у тенант-мережі блокується, і єдиним шляхом назовні залишається явно вказаний проксі-сервер, доступний через інтерфейс PSC. Саме з цієї причини периметр вмикається на Фазі 3 — ще до появи першого агента в продакшені.

**Secure Web Proxy** стає цим єдиним виходом, але змінна середовища `HTTP(S)_PROXY`, яка скеровує туди агентів, — це лише налаштування для зручності, а не механізм захисту. Стандартні HTTP-клієнти враховують її, проте шкідливий код легко її проігнорує. Реальне примусове блокування працює на нижчому рівні й реалізується по-різному залежно від середовища виконання:

- **GKE та Cloud Run:** правила файрвола для вихідного трафіку (egress) блокують усе, крім адреси проксі-сервера та приватного діапазону Google API (`restricted.googleapis.com`); Cloud NAT обслуговує виключно підмережу проксі; сервіси Cloud Run примусово завертаються у VPC політикою `run.allowedVPCEgress = all-traffic`. Якщо код спробує проігнорувати змінну проксі й звернутися в мережу напряму, пакети будуть просто відкинуті файрволом.
- **Рантайм Agent Platform:** примусова ізоляція забезпечується периметром VPC-SC, як описано вище. Жодне правило файрвола у вашій VPC не зупинить трафік, який у неї навіть не заходить.

Обидва сценарії верифікуються однаково — практичною спробою обійти встановлені обмеження (розділ 8).

## 7. Ідентичність: один агент, один принципал, один датасет

Перше, що варто перевірити під час аудиту будь-якої агентної системи, — це найстаріший антипатерн хмарної безпеки: коли декілька агентів використовують один спільний сервісний акаунт із роллю `Editor` або широкими правами доступу до даних. Зламайте одного такого агента — і ви отримаєте контроль над усіма, а в логах аудиту буде неможливо встановити, який саме агент виконав шкідливий запит.

Стандарт ідентичності в нашій landing zone:

- **Агенти в рантаймі Agent Platform, Gemini Enterprise та Cloud Run** отримують нативну **IAM agent identity** — індивідуальний SPIFFE-принципал, який автоматично видається платформою:

  ```text
  principal://agents.global.org-ORG_ID.system.id.goog/resources/aiplatform/
      projects/PROJECT_NUMBER/locations/LOCATION/reasoningEngines/ENGINE_ID
  ```

  Облікові дані жорстко прив'язані до сертифікатів (certificate-bound): агенти автентифікуються в Google API через mTLS відповідно до керованої політики Context-Aware Access, а при проходженні трафіку через Agent Gateway додатково застосовується криптографічна прив'язка токенів DPoP. Токен, викрадений із рантайму, неможливо використати за його межами.
- **Агенти в кластерах GKE** наразі не підтримують нативний механізм agent identity. Тому кожен такий агент отримує власний окремий Google Service Account через Workload Identity Federation for GKE — за суворим правилом «один агент — один акаунт» без жодних винятків.
- **Користувацьких статичних ключів не існує в принципі** — їх створення заблоковано на рівні організації політикою з розділу 4.

Делегування завдань між агентами — це місце, де найчастіше порушується принцип найменших привілеїв, оскільки видати широку роль `roles/aiplatform.user` на весь проєкт значно простіше. У нашій landing zone батьківський агент отримує рівно один дозвіл на виклик рівно одного дочірнього субагента, що описується кодом:

```hcl
resource "google_organization_iam_custom_role" "agent_query_only" {
  org_id      = "ORG_ID"
  role_id     = "reasoningEngineQueryOnly"
  title       = "Reasoning Engine Query Only"
  permissions = ["aiplatform.reasoningEngines.query"]
}

resource "google_vertex_ai_reasoning_engine_iam_member" "parent_queries_subagent" {
  project          = "prj-agent-runtime-prod"
  region           = "europe-west4"
  reasoning_engine = "SUBAGENT_ENGINE_ID"
  role             = google_organization_iam_custom_role.agent_query_only.name
  member           = "principal://agents.global.org-ORG_ID.system.id.goog/resources/aiplatform/projects/PRJ_RUNTIME_NUMBER/locations/europe-west4/reasoningEngines/PARENT_ENGINE_ID"
}
```

Пошук та виявлення агентів (discovery) відбувається виключно через приватний **Agent Registry**. Оскільки сама специфікація протоколу A2A залишає криптографічний підпис карток агентів опціональним, наша landing zone робить його обов'язковим: агент-ініціатор відхиляє будь-які непідписані картки або картки, підписані ключами поза корпоративним центром сертифікації (root of trust), ще до моменту делегування завдання.

Поверх рівня ідентичності працює рівень контролю трафіку в рантаймі, детально описаний у [статті про AI Gateway](#ai-gateway-enforcement): **Agent Gateway** у зв'язці з **Model Armor** перевіряє вхідні промпти, а також вихідні виклики інструментів, їхні відповіді та A2A-повідомлення. При цьому на рівні всієї організації задаються **мінімальні базові налаштування (floor settings)**, щоб жодна команда не змогла застосувати шаблон фільтрації, слабший за поріг, встановлений службою безпеки. Agent Gateway, Agent Registry та інтеграція Model Armor для шлюзу перебувають у статусі GA з червня 2026 року — це повноцінний продакшен-інструментарій, а не експериментальне прев'ю.

## 8. Доказова база: перехід від «Налаштовано» до «Примусово»

Архітектурна діаграма landing zone — це лише декларація намірів. Перетворити її на доведений факт допомагають три рівні зрілості з нашої методики оцінювання:

- **Документовано (Documented)** — правило описане в регламенті чи корпоративній вікі.
- **Налаштовано (Configured)** — параметр увімкнено в конфігурації, але технічно ніщо не заважає його обійти.
- **Примусово (Enforced)** — будь-яка спроба обійти обмеження призводить до блокування деплою, падіння пайплайну або розриву мережевого з'єднання.

У [статті про AI Gateway](#ai-gateway-enforcement) ми ввели поняття тесту на обхід шлюзу (**Gateway Bypass Test**). У масштабі landing zone цей тест розширюється у двох напрямках.

**Він охоплює керовані безсерверні рантайми.** У кластері GKE тестові перевірки (probes) запускаються безпосередньо всередині пода агента командою `kubectl exec`. У керованому рантаймі Agent Platform немає подів, до яких можна підключитися, тому ті самі діагностичні скрипти пакуються як службовий інструмент *разом* із кодом агента і записують результати перевірок у захищений від видалення (locked) бакет логів.

**Він перевіряє всі можливі шляхи успадкування прав.** Агент, якому не видано пряму роль для виклику моделей у власному проєкті, усе одно може успадкувати її з батьківської папки, отримати через членство в Google-групі або через групову прив'язку (`principalSet`), відкриту для всього домену довіри агентів. Простий скрипт, який перевіряє лише локальну IAM-політику проєкту на точний збіг з ім'ям акаунта агента, пропустить усі три непрямі шляхи і видасть хибний статус PASS. Перевірка на рівні landing zone формулює запит так само, як права обчислює сам рушій IAM: через аналізатор політик Cloud Asset Inventory з розгортанням вкладених груп по всьому дереву ієрархії ресурсів спеціально для пермішенів інференсу. Окремий прохід сканера шукає широкі прив'язки `principalSet://` на домені агентів, оскільки один такий запис миттєво відкриває доступ усьому флоту. Тільки за таких умов статус PASS гарантує, що обхідного шляху до моделі справді немає, а не просто що в конфігу відсутній один конкретний рядок.

У поєднанні з мережевими тестами прямого й проксованого виходу в інтернет, а також скануванням змінних середовища на наявність забутих секретів чи токенів, це формує мінімальну доказову базу для контролю межі досяжності (Reach boundary). У повному шаблоні кожна з вісімнадцяти перевірок безпеки (сімнадцять базових плюс нова перевірка R7) має відповідну автоматизовану команду верифікації.

## 9. Розгортання: контрольні гейти замість дат у календарі

Найскладніше у впровадженні landing zone — не написати модулі Terraform, а натягнути захисні обмеження на живу організацію з десятками працюючих сервісів, нічого при цьому не поклавши. Саме тому процес розгортання побудований **навколо контрольних гейтів (gate-driven)**: кожна фаза має чіткі критерії виходу, які своїм підписом підтверджують керівники напрямків Security та Platform, а наступна фаза починається лише після успішного проходження поточного гейту. Календарні дати залишаються в проєктному плані: терміни можуть зсуватися, але це не повинно створювати ілюзії, ніби вимоги безпеки можуть зсуватися разом із ними.

| Фаза | Основні роботи | Критерії виходу з гейту (Exit criteria) |
|---|---|---|
| **0 — Інвентаризація (Discovery)** | Пошук усіх проєктів з увімкненими AI API, публічних сервісів Cloud Run та створених вручну ключів сервісних акаунтів | 100% AI-активів внесено до реєстру із закріпленими власниками; затверджено план усунення знайдених порушень |
| **1 — Базові обмеження** | Організаційні політики в режимі dry-run → усунення порушень → переведення в примусовий режим | Усі базові політики переведено в блок `spec`; для кожної зафіксовано успішний негативний тест у CI |
| **2 — Ієрархія та білий список моделей** | Створення структури папок за середовищами; allowlist моделей для prod; посилення захисту Cloud Run / GKE / Workbench | Продакшен не може викликати незатверджені моделі чи запускати `:tune`; пісочниця (sandbox) повністю ізольована |
| **3 — Периметр і приватний вихід** | VPC-SC у dry-run → примусовий режим для sandbox → non-prod → prod; підключення PSC-I; запуск Secure Web Proxy | Нуль нерозібраних порушень VPC-SC; тестовий агент не може вивести дані назовні чи напряму вийти в інтернет |
| **4 — Рівень управління агентами** | Розгортання Agent Registry, перехід на agent identities, межі доступу, запуск Agent Gateway | Шлюз блокує виклики незареєстрованих інструментів; 100% прод-агентів мають індивідуальну ідентичність; 0 спільних SA |
| **5 — Gemini Enterprise та MCP** | Налаштування CMEK, активація трьох зв'язаних політик, ізоляція винятку ingress в окремому проєкті, перевірка анотацій | Погоджені інструменти працюють; несанкціоновані FQDN блокуються; перевірено дотримання списків доступу (ACL) до документів |
| **6 — Захист контенту та реліз** | Базові налаштування (floor settings) і шаблони Model Armor; незмінні логи (locked logging); навчання red-team | Непрямі промпт-ін'єкції, ескалація привілеїв через інструменти, SSRF та міжтенантні атаки блокуються з генерацією алертів; фінальний підпис CISO |

Фаза 0 — це етап, який команди постійно намагаються проскочити, чого робити категорично не можна. Неможливо захистити робочі навантаження, про існування яких ви навіть не здогадуєтеся, а перелік агентів, відомий платформеній команді, майже ніколи не збігається з реальною картиною по компанії. Запит у Cloud Asset Inventory дає відповіді на три головні запитання в масштабі всієї організації: у яких проєктах активовано AI API, які сервіси стирчать у публічний інтернет з доступом для всіх охочих, і де досі лежать статичні ключі сервісних акаунтів. Результати цієї ревізії зазвичай суттєво коригують подальший план робіт.

## 10. Дев'ять підводних каменів, на які ви обов'язково натрапите

Це ті інженерні деталі, яких ніколи не видно на красивих презентаційних схемах, але які неминуче виринають під час розбору аварій та інцидентів. Кожен із цих пунктів задокументований у довідці Google — проблема лише в тому, що вони розкидані по десятках різних сторінок.

1. **Ключ CMEK для Gemini Enterprise необхідно зареєструвати ще до створення першого сховища даних (data store).** Шифрування CMEK підтримується лише для мультирегіональних ресурсів у локаціях `us` та `eu`, але не в `global`. Усі сховища, створені до реєстрації ключа, назавжди залишаться зашифрованими стандартними ключами Google, а перевести вже створений застосунок чи конектор на власний ключ заднім числом неможливо. Спочатку зареєструйте ключ (у Terraform за це відповідає ресурс `google_discovery_engine_cmek_config`) і видайте сервісному агенту Discovery Engine роль `cryptoKeyEncrypterDecrypter`, і лише *після цього* створюйте сховища.
2. **Периметр VPC Service Controls так само потрібно увімкнути до створення першого сховища даних.** Google не підтримує додавання проєкту Gemini Enterprise у периметр, якщо всередині нього вже існують створені data stores; єдиний вихід у такій ситуації — повне видалення всіх ресурсів і створення їх заново. Саме з цієї причини Фаза 3 в нашому плані передує Фазі 5.
3. **Обмеження `gcp.resourceLocations` одним конкретним регіоном зламає Gemini Enterprise.** Застосунки цієї платформи розгортаються виключно в мультирегіонах `global`, `us` або `eu`, а частина залежних ресурсів — зокрема глобальні налаштування Model Armor (floor settings) — існують лише в локації `global`. Тому в політиці потрібно дозволити комбінацію `in:eu-locations` плюс `global`. І варто пам'ятати: політика `gcp.resourceLocations` обмежує місце фізичного *зберігання стану* ресурсів, але не контролює регіон, у якому виконується інференс моделі. Локалізація обчислень під час інференсу регулюється білим списком моделей і вибором конкретного регіонального ендпоінта.
4. **Політика `restrictNonCmekServices` заблокує роботу сервісів, які неявно створюють службові бакети (про що ви могли й не здогадуватися).** Класичний приклад — дефолтні бакети для збереження вихідного коду та логів збірки в Cloud Build. Створюйте бакети з підтримкою CMEK заздалегідь і явно вказуйте їх у конфігураціях інструментів. Там, де це технічно неможливо, оформлюйте точковий виняток на рівні окремого проєкту виключно для CI/CD-інфраструктури — із записом у реєстрі, щоквартальним переглядом і суворою забороною застосовувати такі винятки до проєктів, де обробляються дані ШІ.
5. **Використання власного домену призводить до тихої втрати ID-токена Cloud Run** під час викликів із боку Gemini Enterprise (розділ 5). На етапі тестування з вимкненими перевірками IAM конектор здається цілком робочим, але при увімкненні захисту раптово падає — або, що значно гірше, їде в продакшен із дірою в авторизації.
6. **Захист VPC-SC для Agent Gateway поширюється лише на шлюзи, створені після 8 вересня 2026 року**, і вимагає використання шаблонів підключення в режимі `ALL_TRAFFIC`. Шлюз, який ви підняли влітку під час пілотного проєкту, не отримає захисту периметра автоматично — одразу закладайте в план його повне перестворення.
7. **Керований рантайм агентів ігнорує правила вашого вихідного файрвола.** Якщо проєкт не закритий периметром VPC-SC, рантайм Agent Platform ходить в інтернет напряму через тенант-мережу Google. Ваші файрволи та проксі-сервери контролюють лише той трафік, який фізично зайшов у вашу VPC. Прямий вихід назовні перекривається виключно периметром VPC-SC (розділ 6).
8. **Ви не зможете відкрити доступ для Gemini Enterprise у периметр за IAM-ідентичністю.** Під час викликів сервісів Cloud Run правила вхідного трафіку (ingress) у VPC-SC не підтримують фільтрацію за конкретними IAM-принципалами. MCP-сервіси для Gemini змушені працювати з мережевим налаштуванням `all`, залишаючись поза захистом периметра для вхідних з'єднань, тому їх необхідно виносити в окремий ізольований проєкт із власним набором компенсувальних механізмів (розділ 5).
9. **Сервіси Memory Bank та Sessions на глобальному ендпоінті не підтримують шифрування CMEK.** Якщо вимога щодо шифрування даних власними ключами є безкомпромісною, підсистему довгострокової пам'яті агента необхідно одразу проєктувати на мультирегіональному або регіональному ендпоінті — це архітектурне рішення потрібно прийняти до того, як у базі накопичаться діалоги клієнтів за цілий рік роботи.

## 11. Що саме вимірювати: метрики ефективності

Топменеджменту не потрібні простирадла з назвами технічних обмежень. Їм потрібні сім чітких показників, які дають однозначну відповідь на запитання, чи тримає удар збудований фундамент:

| Показник (KPI) | Цільове значення |
|---|---|
| Покриття інфраструктури політиками як кодом (org policies, периметри, права доступу в Terraform / GitOps) | 100%, усі винятки зафіксовано в реєстрі |
| Кількість створених вручну ключів сервісних акаунтів | 0 |
| Частка продакшен-агентів із персональною IAM-ідентичністю (agent identity) | 100% |
| Кількість маршрутів на шлюзі до незареєстрованих MCP-ендпоінтів | 0 |
| Кількість продакшен-навантажень на моделях, до виведення яких з експлуатації залишилося < 30 днів | 0 |
| Кількість продакшен-агентів без налаштованого ліміту токенів на рівні шлюзу | 0 |
| Середній час реакції на критичні спрацювання Model Armor / VPC-SC (MTTD / MTTR) | < 60 хвилин |

Підтримувати ці показники в зеленій зоні допомагає чіткий операційний ритм: щотижневий розбір статистики блокувань і відмов у доступі; щомісячний перегляд білого списку моделей та нових обмежень безпеки GCP (Google регулярно випускає нові керовані політики для AI-сервісів); щоквартальна ресертифікація доступів агентів і практичні навчання red-team; двічі на рік — тренувальне відновлення даних із резервних копій, зашифрованих ключами CMEK. І раз на місяць корисно ставити поруч дві цифри: вартість утримання самої платформи безпеки (проксі, NAT, KMS-ключі) та обсяг витрат на токени моделей, які ця платформа захищає.

## Висновок: погодьте фундамент один раз

В організаціях, які застрягли в сірій зоні між успішним пілотом і промисловою експлуатацією, сценарій зазвичай повторюється один в один. Поява кожного нового агента перетворюється на окремі виснажливі перемовини з комітетом із безпеки: до яких систем він має доступ, під чиїм акаунтом ходить у базу, куди відправляє корпоративні дані, хто перевіряв код його інструментів. Узгодження розтягується на тижні, вимоги різняться залежно від того, хто саме проводить рев'ю, а черга на реліз росте швидше, ніж пропускна здатність відділу інформаційної безпеки.

AI landing zone докорінно змінює саму постановку питання. Служба безпеки один раз погоджує **платформу** — її організаційні політики, мережеві периметри, модель ідентичності та контрольні гейти, кожен із яких підкріплений автоматичним тестом, що червоніє при спробі вимкнути захист. Після цього кожному наступному агенту більше не потрібен окремий цикл бюрократичних дебатів. Йому достатньо стати на готовий фундамент і пройти стандартний автоматизований пайплайн перевірок нарівні з іншими.

Саме в цьому полягає різниця між компанією, у якої є написані AI-агенти, і компанією, яка здатна безпечно експлуатувати їх у продакшені.

**Оцініть власний фундамент.** Репозиторій [Agent Platform Security Assessment](https://github.com/d3ep0ps/agent-security-assessment) доступний у відкритому доступі на GitHub. Протестуйте за допомогою нього саму landing zone, а не окремого агента, і подивіться, скільки захисних бар'єрів у вашій інфраструктурі реально забезпечуються платформою (*Enforced*), а не тримаються на чесному слові авторів системних промптів.

### Післямова: як прибрати вхідний виняток із розділу 5 за допомогою Agent Gateway

Після публікації найчастіше запитання стосувалося пастки з розділу 5. Gemini Enterprise викликає кастомні MCP-сервери з інфраструктури Google, а не з вашої VPC. Через це інструмент, який мав би бути суто внутрішнім, змушений приймати публічний вхідний трафік, що виводить вхідні виклики з-під захисту периметра VPC Service Controls.

Відповідь у основній частині статті — локалізація ризику: виділений проєкт для MCP-інструментів Gemini Enterprise, право виклику Cloud Run (`roles/run.invoker`) лише для сервісного агента Discovery Engine, перевірка кожного виклику через Model Armor та окремі ідентичності для інструментів читання й запису. Це працює, але залишається задокументованим винятком.

Тепер у документації Google з'явився спосіб прибрати цей виняток. Gemini Enterprise може маршрутизувати вихідні виклики до кастомних MCP-серверів через Agent Gateway замість звернення через інтернет:

```text
Gemini Enterprise → Agent Gateway → приватне мережеве приєднання (network attachment) у вашу VPC → MCP-сервер на Cloud Run із внутрішнім входом (internal ingress)
```

Доступними є лише інструменти, зареєстровані в Agent Registry, а IAP авторизує кожен виклик інструменту окремо. Сервісу більше не потрібен публічний вхід, тож потреба у винятку зникає. Повне налаштування описано в практичному посібнику Google: [Gemini Enterprise with Agent Gateway egress to a private custom MCP server](https://codelabs.developers.google.com/agw-ge-custom-mcp-egress-vpc-registry).

Обмеження, які варто перевірити перед впровадженням:

- **Регіони:** наразі підтримуються лише `us-central1` та `europe-west1`.
- **Сертифікати:** кінцеві точки MCP все ще потребують публічно довіреного TLS-сертифіката, навіть під час роботи через приватний маршрут.
- **Периметр:** у посібнику не налаштовується VPC Service Controls, тому сумісність цієї зв'язки з периметром потрібно протестувати у власному середовищі.
- **Зрілість:** стадія релізу (launch stage) явно не вказана — перед використанням у промисловому середовищі уточніть статус General Availability (GA).

Там, де ці обмеження не дозволяють використати новий маршрут, схема локалізації з розділу 5 залишається основним резервним варіантом.
