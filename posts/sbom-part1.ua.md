# Безпека як код: Айсберг залежностей та агентний DevSecOps (Частина 1 з 3)

> **"Довіряй, але перевіряй. У ланцюжках постачання програмного забезпечення не довіряй взагалі нікому — перевіряй усе."**

У попередніх статтях блогу d3ep0ps ми налаштовували контейнеризовані сервіси, шлюзи Traefik та конвеєри CI/CD. Але в сучасних програмних системах звичайної піктограми замка в адресному рядку браузера вже недостатньо. TLS захищає *канал зв'язку* — він гарантує, що ви спілкуєтеся з потрібним сервером. Проте він нічого не говорить про безпеку коду, який на ньому виконується.

Атака на SolarWinds у 2020 році не зламала TLS. Вразливість нульового дня Log4Shell у 2021 році не використовувала слабке шифрування. Обидві атаки пройшли через ідеально валідні, правильно налаштовані HTTPS-з'єднання. Вони експлуатували зовсім інше: **довіру в ланцюжку постачання програмного забезпечення (software supply chain)**.

Ця серія статей присвячена усуненню цієї прогалини. Ми побудуємо **Безпечну фабрику програмного забезпечення (Secure Software Factory)** — конвеєр, де кожен артефакт інвентаризується, кожна залежність сканується, кожен образ підписується, а кожне розгортання контролюється політиками безпеки.

У **Частині 1** ми розберемо айсберг залежностей, оптимізацію файлів блокування за допомогою `uv` та автоматизацію аудитів залежностей за допомогою AI Agent Skills безпосередньо у процесі розробки.

## 2. Айсберг залежностей

Ось питання, на яке більшість інженерів не можуть відповісти для своїх власних систем: *скільки пакетів міститься у вашому контейнері в продакшені?*

Для AI-агента на Python відповідь зазвичай вражає. Ваш `requirements.txt` може містити 15 прямих залежностей. Але кожен із цих 15 пакетів має свої залежності, які мають свої власні залежності. Додайте сюди пакети базового образу ОС, фреймворк Google ADK, Google Cloud SDK та numpy (який тягне за собою цілу екосистему C-розширень).

Типовий образ Python AI-агента містить від 300 до 600 встановлених пакетів. Ви написали код лише для 20 з них. Інші 580 надійшли з PyPI, пакетного менеджера ОС та базового образу. Більшість із них ви ніколи не читали, не перевіряли й навіть свідомо не обирали.

Це і є **айсберг залежностей**. Те, що ви бачите (ваш код) — це лише 10% над водою. Те, що реально виконується — це 90% під нею.

```
       \  /
    --- \/ --- (Ватерлінія)
       /  \
      /    \
     /      \  <- 90% Транзитивних залежностей (PyPI, пакети ОС)
    /________\
```

Вразливість **Log4Shell** продемонструвала це наочно у грудні 2021 року. Вразливість віддаленого виконання коду CVE-2021-44228 у `log4j-core` отримала оцінку CVSS 10.0 (максимум). Хоча патч випустили за лічені дні, триаж вразливості зайняв у багатьох компаній *тижні*, оскільки спочатку потрібно було відповісти на просте питання: *чи використовуємо ми взагалі log4j?*

Команди з налагодженим інвентарем залежностей відповіли на це питання за хвилини одним запитом. Команди без нього — вручну перевіряли сотні мікросервісів. Різниця полягала не в інструменті безпеки, а в дисципліні знання того, що саме ви запускаєте, заздалегідь.

AI-системи лише ускладнюють ситуацію. AI-агенти використовують величезні ML-фреймворки (PyTorch, TensorFlow), клієнтські бібліотеки LLM (`google-generativeai`, `openai`, `anthropic`), інструменти обробки даних (`pandas`, `numpy`, `arrow`) та клієнти векторних баз даних. Поверхня атаки є дійсно великою.

**Software Bill of Materials (SBOM)** — це рентгенівський знімок, який робить цей айсберг видимим.

### Перша лінія оборони: Фіксація залежностей

Безпека ланцюжка постачання починається в коді. Якщо ваш `requirements.txt` містить нефіксовані версії залежностей (наприклад, `requests>=2.28.0`), ваші збірки стають недетермінованими. Мінорний патч-реліз на PyPI із шкідливим кодом або зламана залежність автоматично потраплять у ваше середовище під час наступної збірки.

Щоб запобігти цьому, ви повинні використовувати файл блокування (lockfile), який містить точну версію та криптографічний хеш кожної прямої та транзитивної залежності.

Сучасні інструменти роблять це елементарно. **uv** — високопродуктивний менеджер пакетів Python від компанії Astral, написаний на Rust — здатний вирішити ваші залежності та згенерувати безпечний хешований маніфест за мілісекунди:

```bash
# Компіляція dependencies з requirements.in та генерація requirements.txt з хешами
uv pip compile requirements.in --generate-hashes -o requirements.txt
```

Компілюючи залежності з хешами, ви гарантуєте, що під час збирання будуть встановлені лише ті пакети, байт-код яких повністю збігається з перевіреним на етапі локальної розробки.

## 3. Чотирирівневий стек безпеки

Повна безпека ланцюжка постачання складається з чотирьох окремих рівнів, кожен з яких запобігає певній категорії проблем:

```
Вихідний код → Збірка → Підпис → Push → Розгортання → Запуск
      │           │        │       │         │
      ▼           ▼        ▼       ▼         ▼
   [tfsec]     [Grype]  [Cosign]  [AR]   [Gatekeeper]
   [Checkov]   [syft]            [scan]  [Bin Auth]
```

*   **Рівень 1 — Інвентаризація (syft + CycloneDX SBOM)**: Знайте кожен компонент у кожному артефакті, який ви постачаєте. SBOM — це машиночитаний маніфест (назва пакету, версія, походження та хеші). Ми використовуємо формат **CycloneDX** — стандарт OWASP з найкращою екосистемою інструментів.
*   **Рівень 2 — Сканування вразливостей (Grype)**: Співставлення інвентарю з відомими базами даних CVE. **Grype** зчитує SBOM або безпосередньо сканує образ, виявляючи вразливості на основі баз NVD та GitHub Advisories.
*   **Рівень 3 — Підпис образів (Cosign + Sigstore)**: Підпис маніфесту образу безпосередньо в реєстрі, що пов'язує його дайджест із перевіреною ідентичністю. Якщо образ не має валідного підпису, він не міг бути створений у вашому довіреному конвеєрі.
*   **Рівень 4 — Контроль розгортання (Gatekeeper + Binary Authorization)**: Блокування запуску невідповідних образів у вашому кластері Kubernetes.

## 4. Практика: Побудова безпечної фабрики (Рівень 1)

Давайте реалізуємо **Рівень 1 (Мінімальний життєздатний захист)**.

### 4.1. Встановлення інструментів

```bash
# Встановлення syft (генератор SBOM)
curl -sSfL https://raw.githubusercontent.com/anchore/syft/main/install.sh | sh -s -- -b /usr/local/bin

# Встановлення Grype (сканер вразливостей)
curl -sSfL https://raw.githubusercontent.com/anchore/grype/main/install.sh | sh -s -- -b /usr/local/bin

# Встановлення Cosign (підпис образів)
curl -sSfL https://github.com/sigstore/cosign/releases/latest/download/cosign-linux-amd64 \
  -o /usr/local/bin/cosign && chmod +x /usr/local/bin/cosign
```

### 4.2. Dockerfile: Швидка та безпечна збірка Python з `uv`

Напишіть `Dockerfile` для агента так, щоб використовувати `uv` для відтворюваних та швидких збірок:

```dockerfile
FROM python:3.11-slim

# Встановлення бінарного файлу uv безпосередньо з офіційного образу
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/

WORKDIR /app

# Копіювання скомпільованого lockfile.
# Цей файл генерується ззовні контейнера через:
#   uv pip compile requirements.in --generate-hashes -o requirements.txt
# Ніколи не запускайте uv pip compile всередині Dockerfile — це дозволить збірці
# непомітно оновити версії залежностей і зламає перевірку хешів.
COPY requirements.txt .

# Встановлення залежностей у системне оточення з перевіркою хешів
RUN uv pip install --system --no-cache -r requirements.txt

COPY . .
```

### 4.3. Генерація CycloneDX SBOM

```bash
# Генерація SBOM із зібраного образу
syft us-central1-docker.pkg.dev/my-project/agents/orchestrator:v1.2.0 \
  -o cyclonedx-json \
  --file orchestrator-sbom.json

# Перегляд виключно Python-пакетів
cat orchestrator-sbom.json | jq '.components[] | select(.type == "library") | {name: .name, version: .version}' | head -30
```

### 4.4. Сканування вразливостей за допомогою Grype

```bash
# Сканування образу напряму
grype us-central1-docker.pkg.dev/my-project/agents/orchestrator:v1.2.0

# Або сканування вже згенерованого SBOM (швидше та консистентніше)
grype sbom:./orchestrator-sbom.json --fail-on critical
```

Grype повертає таблицю знахідок, відсортованих за рівнем загрози:

```
NAME                          INSTALLED    FIXED-IN     TYPE       VULNERABILITY     SEVERITY
cryptography                  41.0.0       41.0.3       python     CVE-2023-38325    HIGH
urllib3                       1.26.11      1.26.17      python     CVE-2023-43804    MEDIUM
Pillow                        9.5.0        10.0.1       python     CVE-2023-44271    MEDIUM
certifi                       2022.12.7    2023.7.22    python     CVE-2023-37920    MEDIUM
requests                      2.28.2       2.31.0       python     CVE-2023-32681    MEDIUM
```

Колонка **INSTALLED** показує поточну версію; **FIXED-IN** вказує версію, у якій помилку виправлено. Якщо поле `FIXED-IN` порожнє, це означає, що апстрім-виправлення ще не існує — задокументуйте це як відомий ризик і встановіть дату наступного перегляду.

## 5. Агентний DevSecOps: Автоматизація аудитів за допомогою AI Agent Skills

Якщо ви розробляєте свої системи за допомогою AI-асистентів розробника (як-от **Antigravity** або **Claude Code**), вам не обов'язково пам'ятати ці комбінації команд. Замість цього ви можете делегувати це завдання за допомогою спеціального інструменту автоматизації — **Agent Skills**.

Замість того щоб тримати всю логіку безпеки локально в одному проєкті, ми можемо централізувати наші правила. Ви можете знайти повну, готову до продакшену версію цього інструменту в нашому публічному репозиторії:

👉 **[d3ep0ps/agents-skills/software_security](https://github.com/d3ep0ps/agents-skills/tree/main/software_security)**

Маючи підключений файл інструкцій у вашому робочому просторі `agents-skills`, ви можете просто попросити вашого AI-асистента:
> *"Запусти повне сканування безпеки репозиторію та згенеруй звіт"*

Агент самостійно зчитає інструкції, запустить `syft`, `grype`, `bandit`, `pip-audit` та `checkov`, збере всі звіти та підготує для вас консолідований дашборд. Це інтегрує глибокий аудит безпосередньо у ваш щоденний цикл написання коду, замість виявлення помилок перед релізом у CI/CD.
