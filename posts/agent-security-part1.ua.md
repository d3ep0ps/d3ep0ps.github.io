# Безпека як код: Безпека AI-агентів — Впровадження промптів та радіус ураження (Частина 1 з 3)

> **"Сендбоксинг визначає, де агент може діяти. IAM визначає, до чого він має доступ. Жоден з них не перевіряє, чи має агент робити це прямо зараз — і саме в цьому розриві живе впровадження промптів."**

Уявіть картину: агент для аналізу даних працює у поді GKE Sandbox, ізольованому на рівні ядра за допомогою gVisor. Його токен Workload Identity обмежений лише двома датасетами BigQuery — нічого зайвого. Периметр VPC Service Controls огортає кожен сервіс, з яким йому дозволено взаємодіяти. Шлюз перевіряє кожен вхідний промпт та кожну вихідну відповідь. На вашій панелі безпеки стоять усі галочки. Саме так виглядає підхід "ми зробили все правильно".

Аж раптом хтось просить агента "підготувати річний звіт", і п'ятдесят тисяч записів клієнтів витікають через бакет зберігання, звичайне завдання експорту та подальший конвеєр обробки даних (downstream pipeline) — усе це налаштувала ваша команда, і все це працює точно за інструкцією.

Жоден засіб контролю не дав збою. Ніхто не пропустив жодного кроку. Це той факт, над яким варто замислитися, перш ніж читати далі.

---

У попередньому циклі статей **"Безпека як код"** ми захистили ланцюжок постачання контейнерів від ноутбука розробника до контролю доступу GKE: SBOM під час збирання, криптографічний підпис та Binary Authorization, що гарантує запуск лише перевірених образів у продакшені. Ця робота чудово відповідає на одне питання: *чи можемо ми довіряти тому, що запускається?*

Але вона нічого не говорить про новішу проблему: що відбувається, коли запущений компонент — це велика мовна модель (LLM), яка отримує інструкції з промпту, документа, електронного листа або відповіді інструменту, що контролюється зловмисником?

Це відкриває нову серію статей про специфічні загрози безпеки ШІ — область атак, яка починається там, де закінчується сканування контейнерів та Binary Authorization. Частина 1 присвячена впровадженню промптів (prompt injection) і, зокрема, тому, як обране середовище виконання для агента — VM, Cloud Run, GKE або повністю керована платформа на кшталт Vertex AI Agent Engine — змінює радіус ураження (blast radius) у разі успішної атаки. Частина 2 розповість про автентифікацію між агентами (A2A). Частина 3 охопить отруєння ваг моделей та ланцюжка постачання.

## 1. Чому тепер це проблема інфраструктури, а не просто чату

У червні 2025 року дослідники оприлюднили вразливість **EchoLeak (CVE-2025-32711)** — атаку zero-click prompt injection проти Microsoft 365 Copilot. Один спеціально сформований електронний лист без будь-якої взаємодії з користувачем змушував Copilot читати внутрішні файли та передавати їх вміст на сервер зловмисника. У травні 2026 року компанія Pillar Security виявила непряме впровадження промпту з оцінкою CVSS 10 у Gemini CLI, що поширювалося через ланцюжок постачання ПЗ. У цей проміжок часу GitHub Copilot, Cursor та навіть власний сервер Git MCP від Anthropic мали задокументовані вразливості до впровадження промптів, які призводили до несанкціонованого виконання команд або витоку даних.

Жоден із цих випадків не є простою забавкою з "джейлбрейком". Це інциденти, коли доступ агента до інструментів — той самий доступ, який ви надали йому для виконання роботи — був перенаправлений вмістом, якому агент ніколи не мав довіряти.

**Пряме впровадження (direct injection)** відбувається, коли зловмисником є сам користувач: він вводить шкідливу інструкцію безпосередньо в чат. **Непряме впровадження (indirect injection)** є значно небезпечнішим для агентів: шкідлива інструкція вбудовується в те, що агент *читає* — вебсторінку, PDF-файл, тікет на GitHub, запрошення в календарі або метадані самого інструменту. Оскільки сучасні LLM не вміють надійно розрізняти "інструкції мого оператора" та "текст, який мене попросили підсумувати", будь-який шлях надходження вмісту до моделі є потенційним шляхом виконання команд.

Для агентів, підключених до серверів MCP, є другий варіант, про який варто згадати: **отруєння інструментів (tool poisoning)**. Шкідливі інструкції містяться не в даних, які обробляє агент, а приховані в *описі* інструменту, потрапляючи в контекст моделі в момент реєстрації інструменту. Інструмент, який виглядає як `get_weather(city)`, може нести в собі невидиму інструкцію, що змушує агента додатково вивантажувати історію розмов. Ось чому MCP є найменш зрозумілою областю атак у поточних моделях загроз більшості платформних команд — це нова межа довіри, якої ще рік тому не існувало.

## 2. Впровадження промптів — це симптом, а не хвороба

Більшість методів захисту від впровадження промптів розглядають це як проблему формулювання: покращення системних промптів, фільтри на вході та виході. Такий підхід є неповним. Ворожий вміст лише експлуатує те, що система вже дозволила зробити — надто широкі повноваження інструментів, пошук без відстеження джерела походження (provenance) та шляхи виконання без чіткої межі між "ідентичністю агента" та "ідентичністю того, що він читає".

Це той самий урок, який ми засвоїли з Binary Authorization, але перенесений на рівень вище. Політика, яку можна обійти, є лише порадою. Системний промпт "ніколи не розкривай таємниці" — це політика, яку можна обійти вдало підібраним абзацом тексту. Але те, що неможливо "вмовити" порушити правила, — це обмежені права доступу IAM (scoped IAM bindings), мережева політика, яка забороняє вихідний трафік (egress) за замовчуванням, та сендбокс, з якого згенерований агентом код не може втекти.

Це переосмислює головне питання статті: не "як нам завадити обманути модель" (зараз це неможливо зробити на 100%), а "коли модель *таки* обмануть, до чого вона зможе дотягнутися?". Відповідь критично залежатиме від того, де працює агент.

## 3. Середовище запуску вашого агента визначає його радіус ураження

Кожен варіант обчислювальних ресурсів GCP для хостингу агента є компромісом між оперативним контролем та зручністю, і цей вибір безпосередньо визначає межу шкоди, яку може завдати успішна атака.

**Compute Engine VM.** Відсутність межі ідентичності на рівні робочого навантаження за замовчуванням. Якщо сервісний акаунт агента використовує прив'язану ідентичність віртуальної машини замість обмеженої, і ніхто її не вимкнув, агент успадкує все, до чого має доступ дефолтний сервісний акаунт Compute Engine (часто це роль Editor у проекті). Немає ізоляції на рівні ядра для коду, який виконує агент. Це найгірший варіант для старту і, за спостереженнями, досі найпопулярніший серед команд, які "просто хочуть, щоб агент десь крутився".

**Cloud Run.** Краще — окремий контейнер для кожної ревізії, виділений (ідеально — з обмеженими правами) сервісний акаунт і відсутність спільної ноди. Проте Cloud Run та Cloud Functions — це саме ті інтеграції, які команди найчастіше забувають помістити *всередину* периметра VPC Service Controls. Якщо ваш агент робить запити через сервіс Cloud Run, який знаходиться поза периметром, цей сервіс стає лазівкою: скомпрометований агент спрямовує дані через "дозволений" виклик Cloud Run і спокійно проходить повз кордон, який, як ви думали, надійно захищає систему.

**GKE.** Тут засоби контролю стають достатньо деталізованими, а поєднання трьох примітивів дає максимальний ефект:

- **GKE Agent Sandbox**, побудований на gVisor, забезпечує ізоляцію на рівні ядра для виконання згенерованого LLM коду з **мережевим правилом default-deny** — ізольований агент не може достукатися до контрол-плейну GKE чи будь-якого внутрішнього сервісу, якщо ви явно не дозволите це в `SandboxTemplate`.
- **Workload Identity Federation** замінює статичні ключі короткочасними токенами для кожного пода, прив'язаними до конкретної ідентичності Google Cloud. У кластерах Autopilot це увімкнено за замовчуванням; у кластерах Standard будь-який пул нод, де це *не* увімкнено, повертається до використання сервісного акаунта ноди — зазвичай це дефолтний сервісний акаунт Compute Engine з доступом рівня Editor. Один неправильно налаштований пул нод руйнує всю модель безпеки.
- **VPC Service Controls** обмежує периметром сервіси, до яких ваш агент має право звертатися — BigQuery, Cloud Storage, Vertex AI, Secret Manager.

Пастка тут криється не в якомусь конкретному рівні, а в припущенні, що ці три компоненти разом дають повний захист. Це не так через одну структурну причину, про яку варто сказати відверто: **IAM перевіряє права доступу (permission), а не паттерн поведінки (pattern).** Якщо прив'язка Workload Identity вашого агента надає роль `roles/bigquery.dataViewer` для набору даних, короткочасний токен абсолютно однаково дозволить і звичайний запит на 500 рядків, і повний експорт таблиці внаслідок атаки prompt injection. Binary Authorization могла б повністю відмовити в запуску неперевіреного образу, оскільки ця перевірка є бінарною. Але обмежена роль IAM не може заблокувати *дозволену* дію лише тому, що змінився намір агента, який її виконує — для цього потрібен аналіз поведінки, а не просто політика.

**Vertex AI Agent Engine / Gemini Enterprise Agent Platform (повністю керована).** Ви відмовляєтеся від прямого контролю над сендбоксом та мережевими межами в обмін на те, що Google бере це на себе. Для багатьох команд це виправданий крок, але статус "керованого" (managed) просто прибирає межу ізоляції з ваших очей, а не скасовує її існування. У березні 2026 року Unit 42 опублікував дослідження ("Double Agents"), яке показало, що облікові дані, отримані зсередини керованого контексту виконання AI-агента, можна було використати для виходу з цього контексту у власний проект клієнта, отримуючи необмежений доступ на читання до кожного бакета Cloud Storage в ньому. Збій стався саме на рівні ізоляції між спільним середовищем виконання платформи та проектом клієнта — межі, яку клієнт не мав можливості самостійно перевірити чи посилити, бо вона не належала йому для налаштування.

| Середовище виконання | Ізоляція згенерованого агентом коду | Обмеження ідентичності (identity scoping) | Хто володіє межею безпеки |
|---|---|---|---|
| Compute Engine VM | Відсутня за замовчуванням | Часто власний сервісний акаунт VM (широкий) | Ви, але зазвичай без контролю |
| Cloud Run | Контейнер для кожної ревізії | Сервісний акаунт на рівні сервісу, легко обмежити | Ви, але легко залишити поза VPC-SC |
| GKE (Autopilot) | gVisor через Agent Sandbox, мережа default-deny | Workload Identity Federation, увімкнено за замовчуванням | Ви, повністю |
| GKE (Standard) | gVisor через Agent Sandbox (потрібно підключити) | Workload Identity Federation (потрібно перевіряти для кожного пулу нод) | Ви, якщо все налаштовано правильно |
| Vertex AI Agent Engine / Gemini Enterprise | Керований сендбокс | Керована ідентичність + ваші права доступу IAM | Спільно з Google — ви не бачите межі між орендарями |

Практичний висновок: GKE надає вам найбільше важелів керування, але кожен із них потрібно реально налаштувати. Керована платформа робить це за вас, але ви змушені довіряти межам безпеки, яких не бачите.

## 4. Model Armor: шлюз, який фільтрує те, що пропускає межа безпеки

Жоден із наведених вище засобів ізоляції та контролю IAM не перевіряє *вміст*. Це завдання Model Armor — сервісу Google Cloud, який аналізує промпти та відповіді на наявність впровадження промптів, спроб обходу захисту (jailbreak), конфіденційних даних та шкідливих URL-адрес, працюючи inline між клієнтом та моделлю.

Model Armor налаштовується за допомогою **шаблонів (templates)** (наборів фільтрів для окремих застосунків) або **мінімальних вимог (floor settings)** (базового рівня безпеки на рівні організації чи проекту, якому має відповідати кожен шаблон — той самий підхід "встановити мінімум, дозволити командам будувати поверх нього", який Binary Authorization використовує для атестації образів). Кожна категорія фільтрів — виявлення впровадження промптів та джейлбрейків, категорії відповідального ШІ, захист конфіденційних даних, шкідливі URL — має свій поріг чутливості (confidence threshold): `High` для робочого трафіку, де небажані хибні спрацьовування, або `Low and above`, коли пропустити реальну атаку набагато гірше, ніж час від часу помилково блокувати легітимні запити. Власна інструкція Google рекомендує починати виявлення впровадження промптів із рівня `Medium` і переходити на `High` лише тоді, коли виникають проблеми з блокуванням нормальних запитів.

Створення шаблону здійснюється одним викликом `gcloud`:

```bash
gcloud model-armor templates create agent-input-template \
  --project=my-project --location=us-central1 \
  --rai-settings-filters='[
    { "filterType": "HATE_SPEECH", "confidenceLevel": "MEDIUM_AND_ABOVE" },
    { "filterType": "HARASSMENT", "confidenceLevel": "MEDIUM_AND_ABOVE" }
  ]' \
  --pi-and-jailbreak-filter-settings-enforcement=enabled \
  --pi-and-jailbreak-filter-settings-confidence-level=MEDIUM_AND_ABOVE
```

Як і у випадку з нашою політикою Binary Authorization, що керується через Terraform, ця конфігурація має бути описана у коді, а не створюватися вручну в консолі:

```hcl
# terraform/model-armor.tf
resource "google_model_armor_template" "agent_input" {
  location    = "us-central1"
  template_id = "agent-input-template"

  filter_config {
    pi_and_jailbreak_filter_settings {
      filter_enforcement = "ENABLED"
      confidence_level    = "MEDIUM_AND_ABOVE"
    }
    sdp_settings {
      basic_config {
        filter_enforcement = "ENABLED"
      }
    }
  }

  template_metadata {
    log_sanitize_operations = true
  }
}

# Базовий рівень для всієї організації: шаблони кожного проекту мають відповідати цьому мінімуму,
# та сама ідея "політики, яку неможливо обійти", що й примусове виконання
# на рівні всього кластера в Binary Authorization.
resource "google_model_armor_floorsetting" "org_floor" {
  parent   = "organizations/${var.org_id}"
  location = "global"

  filter_config {
    pi_and_jailbreak_filter_settings {
      filter_enforcement = "ENABLED"
      confidence_level    = "MEDIUM_AND_ABOVE"
    }
  }

  enable_floor_setting_enforcement = true

  # Керує застосуванням правил саме для трафіку Vertex AI / Gemini traffic;
  # саме inspect_and_block, а не inspect_only, робить це бар'єром,
  # а не просто логуванням.
  ai_platform_floor_setting {
    inspect_and_block    = true
    enable_cloud_logging = true
  }
}
```

Місце, де Model Armor фактично перехоплює трафік, залежить від вашої архітектури, і це безпосередньо впливає на обговорення радіусу ураження вище:

- **Пряма інтеграція з Vertex AI/Gemini** — перевірка в реальному часі під час викликів `generateContent`, не потребує змін у коді, але працює лише для моделей Gemini.
- **Agent Gateway** (частина Gemini Enterprise Agent Platform) — проксі контрол-плейну з двома точками контролю: **Клієнт-Агент (ingress)**, що фільтрує вхідні запити до агента та його відповіді, та **Агент-Усюди (egress)**, що контролює запити агента до зовнішніх LLM, інших агентів чи серверів MCP, а також результати від них. Фільтрація вихідного трафіку (egress) є критичною для захисту від непрямого впровадження промптів та отруєння інструментів — це вузьке місце контролю між вашим агентом та неперевіреним вмістом, який він отримує.
- **GKE через Service Extensions** — розширення сервісу на вашому балансувальнику навантаження або шлюзі GKE Inference Gateway для агентів, які ви хостите самостійно, а не запускаєте через Gemini Enterprise.
- **Сервери MCP** (Preview) — базові налаштування (floor settings), які застосовуються безпосередньо до викликів та відповідей інструментів MCP Google та Google Cloud.

Варто згадати про одне обмеження, щоб воно не стало сюрпризом згодом: інтеграція Model Armor з Gemini Enterprise очищає лише *початковий* промпт та *фінальну* відповідь. Проміжні кроки — виклики інструментів та проміжні результати між ними — не охоплюються цим конкретним шляхом інтеграції; саме для цього призначені вихідна фільтрація Agent Gateway та шлях GKE Service Extensions.

## 5. Ідентичність в ADK та її пряме підключення до IAM замість накладання безпеки потім

Agent Development Kit розглядає безпеку як невід'ємну частину фреймворку, а не як фільтр, який додається згодом. Його модель безпеки складається з трьох рівнів, які чітко відповідають усьому описаному вище:

1. **Ідентичність та авторизація.** Інструменти ADK діють від імені однієї з двох ідентичностей: **agent-auth** (сервісний акаунт самого агента) або **user-auth** (ідентичність користувача, який запускає агента). Це одне рішення визначає практичну реалізацію "обмеження доступу IAM" для агентів — воно вказує, чий саме радіус ураження діятиме при збої виклику інструменту. Компонент **Agent Identity Auth Manager** керує життєвим циклом OAuth для потоків user-auth: зберігає конфігурації облікових даних, випускає та зберігає токени, а також логує кожен доступ, розвантажуючи вас від потреби створювати власне сховище токенів.
2. **Запобіжники (Guardrails).** Тут підключається Model Armor разом із колбеками ADK, які можуть перевіряти виклики інструментів до або після їхнього виконання. Рекомендації Google радять використовувати швидку та дешеву модель (Gemini Flash Lite) як рівень попередньої перевірки перед основним агентом — для виявлення явно шкідливих запитів до того, як вони витратять ресурси на повноцінний виклик моделі.
3. **Ізольоване виконання (Sandboxed execution).** Тут працює Agent Sandbox на GKE або керований сендбокс Agent Engine, виконуючи роботу, описану в розділі 3.

Помилка в IAM, яка нівелює весь цей захист, аналогічна тій, яку роблять команди з Binary Authorization: надання занадто широкої ролі, бо так швидше. У власному коді з практичного керівництва Google для розгортання агентів на GKE роль `roles/aiplatform.user` надається на рівні **всього проекту** — що дозволяє агенту викликати інференс на будь-якій кінцевій точці проекту та бачити всі моделі. Для вузькоспеціалізованого агента обмежте його права:

| Що потрібно агенту | Надлишкові права (рівень проекту) | Правильно обмежені права (рівень ресурсу) |
|---|---|---|
| Викликати один інференс-ендпоінт | `roles/aiplatform.user` на рівні проекту | `roles/aiplatform.user` на рівні цього конкретного ендпоінту |
| Читати один набір даних BigQuery | `roles/bigquery.dataViewer` на рівні проекту | `roles/bigquery.dataViewer` для цього набору даних |
| Читати один бакет | `roles/storage.objectViewer` на рівні проекту | `roles/storage.objectViewer` для цього конкретного бакета |

```hcl
# terraform/agent-identity.tf
resource "google_service_account" "invoice_agent" {
  account_id   = "invoice-agent"
  display_name = "Invoice summarization agent (agent-auth)"
}

# Рівень ресурсу, а не рівень проекту.
resource "google_bigquery_dataset_iam_member" "agent_dataset_read" {
  dataset_id = google_bigquery_dataset.invoices.dataset_id
  role       = "roles/bigquery.dataViewer"
  member     = "serviceAccount:${google_service_account.invoice_agent.email}"
}

# Прив'язка Workload Identity Federation — под GKE до цього SA, нічого ширшого.
resource "google_service_account_iam_member" "wif_binding" {
  service_account_id = google_service_account.invoice_agent.name
  role                = "roles/iam.workloadIdentityUser"
  member              = "serviceAccount:${var.project_id}.svc.id.goog[agents/invoice-agent]"
}
```

У поєднанні з `SandboxTemplate`, який забороняє вихідний трафік за замовчуванням (окрім специфічних кінцевих точок BigQuery та Vertex AI, потрібних цьому агенту), та налаштуванням Model Armor, яке перевіряє все на Agent Gateway, ви будуєте багаторівневий захист, подібний до Binary Authorization: жоден елемент контролю не має бути ідеальним, оскільки збій одного компенсується межею наступного.

## 6. Що це не вирішує

Будьте чесними щодо залишкового ризику: навіть якщо всі засоби контролю з цієї статті налаштовані правильно — обмежений Workload Identity, сендбокс із правилом default-deny, VPC-SC, Model Armor на вході та виході — жоден із них не зможе відрізнити звичайний запит агента на 500 рядків від експорту всієї таблиці через атаку prompt injection, якщо обидві дії технічно дозволені політикою. Це питання поведінки, а не політики, і саме тому моніторинг поведінки агентів у реальному часі (runtime monitoring) стає окремою дисципліною, а не просто другорядною деталлю. І саме тому описана в статті архітектура має першочергове значення: що меншим є набір "технічно дозволених" дій, то меншим стає цей залишковий ризик.

## Що далі
