
# Диригент: Автоматизація Стеку

> **"Якщо це треба набрати двічі, напиши скрипт. Якщо це треба заскриптувати двічі, автоматизуй це."**

У нашій останній статті, "Приборкання Звіра", ми розібрали наш монолітний сервер та ізолювали наші сервіси.

* **Apache** безпечно працює в Jail.
* **MySQL** ізольовано в Контейнері.
* **Мережа** керується віртуальними мостами (bridges).

Але ми створили новий ризик.
Щоб побудувати це, ми набрали десятки команд. `zfs clone`, `ifconfig bridge0`, `lxc launch`, `pkg install`.

Якщо сервер згорить сьогодні, чи зможете ви відновити його точнісінько таким, яким він був, за 15 хвилин?
Якщо вас зіб'є автобус, чи знає хтось інший, що `web01` залежить від специфічного параметра `sysctl`, який ви встановили о 2-й ночі?

Це **"Фактор Автобуса" (Bus Factor).** Прямо зараз ваш Bus Factor дорівнює 1.
Щоб масштабуватися, нам треба припинити ставитися до наших серверів як до "Домашніх улюбленців" (Pets), яких ми виходжуємо. Ми повинні ставитися до них як до "Худоби" (Cattle). Ми не лікуємо їх; ми їх замінюємо. Сподіваюся аналогія не дуже жорстка.

Щоб зробити це, нам потрібен **Диригент**. Нам потрібна **Infrastructure as Code (IaC)**.



## 1. Філософія: Імперативний проти Декларативного

Перш ніж обирати інструменти, ми повинні обрати мислення.

**Імперативне мислення (Скрипт):**
Це те, що ми робили в терміналі.

> *"Спочатку створи bridge0. Потім створи jail. Потім встанови Nginx."*
> Якщо ви запустите цей скрипт двічі, він може зламатися (наприклад, "Error: bridge0 already exists"). Ви повинні керувати станом самостійно.

**Декларативне мислення (Креслення):**
Це те, що ми хочемо.

> *"Має бути bridge0. Має бути jail, в якому працює Nginx."*
> Ви визначаєте *кінцевий стан*. Інструмент з'ясовує, як цього досягти. Якщо міст існує, він нічого не робить. Якщо його немає, він його створює.




## 2. Еволюція IaC: Від Патчів до Креслень(blueprints)

"Infrastructure as Code" — це не один інструмент; це спектр інструментів, котрі еволюціонували.

**Фаза 1: Управління Конфігурацією (Ера VM)**
У світі Віртуальних Машин (як у моїй [ansible-lab](https://github.com/d3ep0ps/ansible-lab)), IaC означало використання інструментів на кшталт **Ansible**, **Chef** або **Puppet**.
Ви запускаєте сервер, а потім застосовуєте код, щоб *змінити* його.

* *Workflow:* Запуск OS -> SSH в середину -> Встановлення пакетів -> Копіювання конфігів.
* *Результат:* Довгоживучий сервер, який постійно патчиться та оновлюється.

**Пастка:**
Коли ми перейшли до Контейнерів, багато інженерів (включаючи мене) намагалися перетягнути цей workflow із собою. Ми ставилися до контейнерів як до "легковагових VM".
Ми запускали контейнер, тримали його працюючим місяцями і використовували Ansible, щоб патчити його.
Хоча це *працює*, це створює значні ризики:

1. **Забруднення залежностей:** Щоб запустити Ansible, вам потрібен Python та SSH *всередині* кожного контейнера. Ви заповнюєте своє ізольоване середовище інструментами управління, які не мають нічого спільного з вашим застосунком.
2. **Дрейф конфігурації:** Якщо ви використовуєте Ansible, щоб патчити працюючий контейнер, цей контейнер тепер унікальний. Якщо він впаде, вам залишається сподіватися, що ваш плейбук ідеально відпрацює на свіжому. Ви все ще управляєте "Улюбленцями", просто меншими.

**Фаза 2: Незмінні Артефакти (Ера Build)**
Щоб справді вирішити проблему "Bus Factor", ми змінили парадигму.
Ми перестали намагатися *конфігурувати* працюючі сервери і почали *будувати* готові до запуску артефакти.

* *Workflow:* Визначення Build-файлу -> Побудова Образу (Image) -> Запуск Контейнера.
* *Результат:* **Immutable Infrastructure (Незмінна Інфраструктура)**. Навіть якщо контейнер працює рік, ми ніколи не патчимо його. Щоб оновити Nginx, ми не перезапускаємо сервіс; ми будуємо новий образ і замінюємо контейнер.

> P.S. Подібний принцип працює і для віртуальних машин: Визначення конфігурації через Packer config -> побудова Golden Image -> запуск нових віртуальних машин.

Це гарантує, що "Креслення" (Dockerfile/Bastillefile) завжди є єдиним джерелом істини.



## 3. Шлях FreeBSD: Bastillefile

У FreeBSD ми впроваджуємо це "Незмінне Креслення", використовуючи **Bastille**.
Bastille дозволяє нам використовувати декларативний шаблон, який називається `Bastillefile`. Він виглядає як скрипт, але ми трактуємо його як визначення збірки (build definition).

Замість того, щоб заходити по SSH на `web01` для встановлення Nginx, ми визначаємо стан `web01` у файлі.

**Креслення (`Bastillefile`):**

```dockerfile
# /usr/local/bastille/templates/project/web/Bastillefile

# 1. Bootstrap the Environment
PKG nginx
PKG git

# 2. Configure the Service (rc.conf)
SYSRC nginx_enable=YES
SYSRC weak_ssl_ciphers=NO

# 3. Inject Configuration
# Copies a file from the host into the jail
CP config/nginx.conf /usr/local/etc/nginx/nginx.conf

# 4. Start the Service
SERVICE nginx start

# 5. Networking (Redirection)
RDR tcp 80 80

```

**Виконання:**

```bash
# 1. Create the Cage (Jail)
# This bootstraps a fresh OS instance on IP 10.0.0.2
bastille create web01 13.2-RELEASE 10.0.0.2

# 2. Apply the Blueprint (Template)
# This runs our PKG, SYSRC, and SERVICE commands inside the running jail
bastille template web01 project/web

```

Це ефективно. Воно використовує інструменти хоста, щоб вносити зміни безпосередньо у файлову систему Jail (ZFS dataset), оминаючи потребу в SSH або агентах всередині Jail.

> На відміну від Docker-образів, шаблони Bastille працюють на запущеному jail, але дисципліна та сама: шаблон залишається єдиним джерелом істини.



## 4. Шлях Linux: Dockerfile

У Linux ця концепція виграла війну. Вона називається **Dockerfile**.
Причина, чому Docker став галузевим стандартом, не в "контейнерах" (у LXC вони були). А в тому, що він вдосконалив цей **Build Workflow**.

У моделі Ansible/VM ви запускаєте чисту ОС і чекаєте, поки встановиться софт.
У моделі Docker ви **вбудовуєте** софт в образ *до того*, як взагалі його запустите.

**Креслення (`Dockerfile`):**

```dockerfile
# 1. Start from a base image (The "debootstrap" layer)
FROM ubuntu:22.04

# 2. Install Dependencies (The "apt" layer)
RUN apt-get update && apt-get install -y nginx

# 3. Copy Config (The "Configuration" layer)
COPY nginx.conf /etc/nginx/nginx.conf

# 4. Define the Process (The "Service" layer)
CMD ["nginx", "-g", "daemon off;"]

```

**Виконання:**

```bash
# Build the artifact (Image)
docker build -t my-web-server .

# Run the artifact (Container)
docker run -d -p 80:80 my-web-server

```

### Чому це підкорило індустрію

1. **Незмінність (Immutability):** Як тільки `my-web-server` побудовано, він ніколи не змінюється. Ви не "оновлюєте" Nginx всередині контейнера. Ви оновлюєте Dockerfile, перебудовуєте образ і замінюєте контейнер.
2. **Кешування:** Docker кешує кожен рядок. Якщо ви змінюєте рядок `COPY nginx.conf`, Docker не перезапускає рядок `apt-get install`. Він перевикористовує закешований шар.
3. **Портативність:** Результатом є єдиний бінарно-подібний об'єкт (Образ), який працює точнісінько так само на моєму ноутбуці, як і на вашому сервері.

## Висновок

Ми успішно автоматизували наш стек, використовуючи сучасні принципи **Infrastructure as Code**.

* **FreeBSD:** Ми використовуємо **Bastillefiles** для шаблонізації наших Jails.
* **Linux:** Ми використовуємо **Dockerfiles** для побудови наших Container Images.

Ми перейшли від **набору команд** до **писання креслень**.
Наша інфраструктура тепер є кодом. Її можна версіонувати в Git, рецензувати колегами і відкочувати, якщо вона зламається.

Але тепер, коли ми маємо ці красиві, ізольовані, автоматизовані чорні скриньки... **як нам зазирнути всередину них?**
В моноліті ми дивилися в `/var/log/syslog`. У розподіленій системі з ефемерними контейнерами логи зникають, коли помирає контейнер.

Нам потрібен новий спосіб спостерігати за системою.
