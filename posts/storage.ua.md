# Сховище: Постійні дані та міграції баз даних

> **"Сервери — це худоба, але Дані — це сімейна реліквія."**

У попередніх розділах **d3ep0ps** ми побудували кластер, що самовідновлюється (**Рій**), та високошвидкісний конвеєр розгортання (**Кузня**).

Ми досягли красивої, високоавтоматизованої архітектури, де код є ефемерним. Якщо контейнер вмирає, планувальник його замінює. Якщо гіпервізор виходить з ладу, робочі навантаження мігрують. Але ми уникали неприємної правди: мікросервіси це легко, тому що вони не мають стану (stateless).

Що відбувається, коли робоче навантаження включає Базу Даних? Якщо планувальник перемістить ваш контейнер PostgreSQL з Вузла А на Вузол Б, контейнер запуститься ідеально, але локальний диск зникне. Ваші дані випарувалися. Код легко переміщати, оскільки він не має стану, але дані мають **гравітацію**. Коли ваш планувальник переміщує базу даних, дані повинні слідувати за нею, інакше ви залишитесь з порожньою оболонкою.

Щоб справді досягти інфраструктури "Zero-Touch", нам потрібно вирішити дві найбільші проблеми стану: **Простір (Постійність)** та **Час (Еволюція)**.

## 1. Гравітація даних: Зберігання в кластері

Як я зазначав у **Рої**, мій досвід роботи з хмарними провайдерами навчив мене критично важливому уроку: сховище має бути відокремлене від обчислень. Ми не зберігаємо дані на локальному жорсткому диску сервера; ми використовуємо **Мережеві сховища (NAS)** або **Розподілені файлові системи**.

### Container Storage Interface (CSI)

У сучасному кластері, незалежно від того, чи використовуєте ви Kubernetes або Nomad, це відокремлення досягається за допомогою **Container Storage Interface (CSI)**. CSI дозволяє інструменту оркестрації динамічно підключати та відключати томи сховища до контейнерів по мірі їх переміщення через фізичні межі.

Наприклад, у нашій лабораторії D3ep0ps на базі Nomad ми використовуємо плагін CSI (наприклад, NFS, Ceph або специфічний драйвер хмарного провайдера). Нашому додатку байдуже, *де* він працює; він просто запитує у планувальника том.

**Шлях D3ep0ps (Фрагмент Nomad CSI):**

```hcl
job "database" {
  group "postgres" {
    # Запит існуючого CSI тому
    volume "db-data" {
      type      = "csi"
      read_only = false
      source    = "postgres-prod-vol"
    }

    task "server" {
      driver = "docker"
      config {
        image = "postgres:15"
      }
      # Монтування мережевого сховища всередині контейнера
      volume_mount {
        volume      = "db-data"
        destination = "/var/lib/postgresql/data"
      }
    }
  }
}
```

Якщо Вузол 1 втрачає живлення, Nomad автоматично переплановує завдання бази даних на Вузол 2, а плагін CSI непомітно відключає сховище від Вузла 1 і підключає його до Вузла 2. Дані слідують за контейнером.

### Виклик POSIX та Split-Brain

CSI вирішує механічну проблему *підключення* сховища, але що відбувається, коли контейнер фактично намагається його *використати*?

Більшість застарілих додатків очікують **POSIX-сумісну** файлову систему — вони хочуть читати та писати файли безпосередньо, ніби вони повністю володіють блоковим пристроєм. Хоча розподілені файлові системи (такі як GlusterFS або Ceph FS) можуть об'єднувати жорсткі диски по мережі та надавати інтерфейс POSIX, вони створюють жахливий ризик "Split-Brain" (розщеплення мозку).

Мережеві розділення (network partitions) *обов'язково* стануться. Коли це відбувається, якщо два вузли втрачають зв'язок один з одним, але обидва вважають себе "Первинними" (Primary), вони обидва наосліп одночасно писатимуть на спільний диск. Це призводить до незворотного пошкодження даних за мілісекунди.

Щоб запобігти цьому, ми повинні запровадити суворе правило для всього кластера: **Один Письменник (Writer) одночасно.** Хоча розподілені системи чудово масштабують операції *читання* (де дані безпечно реплікуються між вузлами), наявність кількох вузлів кластера, які одночасно пишуть в одну файлову систему без розподіленого менеджера блокувань (distributed lock manager), є архітектурним самогубством. Ми з радістю жертвуємо невеликою затримкою запису (очікування блокування) заради абсолютної цілісності даних.

## 2. Масштабування ядра: Репліки та Шардинг

Коли наш додаток переростає можливості одного спільного диска, ми переносимо логіку з рівня файлової системи на **рівень Бази даних**. Сам рушій бази даних стає відповідальним за управління кластером.

* **Master-Replica (Active-Passive):** Найпоширеніший підхід. Ми призначаємо один екземпляр "Первинним" (Primary — єдиний, якому дозволено запис) і кілька "Реплік для читання" (Read Replicas). Це дозволяє нам нескінченно масштабувати навантаження на читання. Первинний обробляє "Джерело істини", тоді як репліки залишаються синхронізованими для обробки запитів.
* **Multi-Master (Active-Active):** Складніше налаштування, де кілька вузлів можуть приймати запис. Такі інструменти, як Galera Cluster або спеціалізовані розподілені SQL бази даних, забезпечують це. Це вирішує проблему єдиної точки відмови для запису, але вводить значні затримки через вимоги синхронної реплікації.
* **Шардинг даних (Data Sharding):** Коли набір даних стає занадто великим, щоб один сервер міг його навіть *вмістити*, або коли ми суворо повинні подолати вузьке місце єдиного письменника без штрафу синхронної Multi-Master реплікації, ми використовуємо шардинг. Ми розділяємо дані горизонтально (наприклад, європейські користувачі на Сервері А, азійські користувачі на Сервері Б). Це переносить складність на рівень додатку, але усуває фізичну стелю для масштабування. Завдяки шардингу кожен шард має власного виділеного письменника, ефективно розпаралелюючи пропускну здатність запису. *Примітка: сучасні хмарні бази даних (як CockroachDB або TiDB) та проміжні програми для шардингу (як Vitess для MySQL) тепер автоматизують цю абстракцію, дозволяючи розробнику розглядати масивний шардований кластер як єдину логічну базу даних.*

## 3. Еволюція: Міграції схем у конвеєрі

Навіть якщо мережеве сховище безпечне та високодоступне, **структура** даних постійно змінюється. Схема — це живий організм.

Якщо людині доводиться вручну заходити в консоль бази даних і запускати команду `ALTER TABLE` перед розгортанням, ваша автоматизація зламана. Гірше того, це створює величезний ризик розсинхронізації між розгорнутим кодом і активною схемою бази даних.

**Стратегія: Схема як код (Schema as Code).**

Ми ставимося до схеми нашої бази даних так само, як і до логіки нашого додатку. Кожна зміна — це пронумерований SQL-скрипт з контролем версій (наприклад, `001_create_users.sql`, `002_add_email_index.sql`), що зберігається разом із вихідним кодом у Git.

У **Кузні** ми використовуємо такі інструменти, як **Flyway**, **Liquibase** або **dbmate**, щоб автоматично застосовувати ці зміни під час розгортання.

**Рукостискання (Хук Nomad `prestart`):**

До того, як новій версії вашого додатку буде дозволено запуститися, запускається "Завдання міграції" (Migration Task). Це визначається як хук життєвого циклу `prestart` у Nomad (або `initContainer` у Kubernetes).

```hcl
task "migrate-db" {
  driver = "docker"
  
  # Виконати це завдання до кінця перед запуском основного додатку
  lifecycle {
    hook    = "prestart"
    sidecar = false
  }

  config {
    image   = "dbmate/dbmate"
    command = ["dbmate", "up"]
  }
}
```

1. **Логіка:** Інструмент перевіряє спеціальну таблицю `schema_version` у базі даних.
2. **Виконання:** Він застосовує лише відсутні скрипти в послідовному порядку.
3. **Ворота:** Тільки якщо міграція проходить успішно, планувальник запускає основний контейнер додатку.

Це гарантує, що **Схема** і **Код** завжди ідеально синхронізовані, назавжди усуваючи помилки "Column not found" у продакшені.

## 4. Остання лінія оборони: Снапшоти та Бэкапи

Висока доступність — це не система резервного копіювання. Реплікована база даних із задоволенням реплікує команду `DROP TABLE users;` на кожен вузол за мілісекунди.

Постійність настільки хороша, наскільки швидким є ваш час відновлення. У лабораторії **d3ep0ps** ми використовуємо багаторівневий, глибоко ешелонований підхід (defense-in-depth):

* **Машина часу (Снапшоти ZFS та LVM):** Якщо наш базовий рівень сховища використовує ZFS на FreeBSD (або OpenZFS на Linux), ми можемо робити миттєві, атомарні снапшоти на рівні блоків. Якщо ми використовуємо традиційні файлові системи Linux, **LVM (Logical Volume Manager)** надає аналогічні можливості снапшотів. Вони не коштують майже нічого з точки зору продуктивності або простору. Якщо автоматизована міграція йде катастрофічно не так, ми можемо "відкотити" весь том до точної секунди перед розгортанням.
* **Нативні бекапи бази даних:** Снапшоти фіксують стан диска, але іноді нам потрібні резервні копії з урахуванням специфіки додатку.
  * *Логічні дампи (Logical Dumps):* Інструменти на зразок `pg_dump` або `mysqldump` експортують базу даних у вигляді звичайного SQL-тексту. Вони повільно відновлюються, але надзвичайно корисні для переміщення даних між різними версіями рушія бази даних або для аудиту.
  * *Фізичні/Точкові (Point-in-Time):* У корпоративних середовищах використовують інструменти на зразок `pgBackRest` або `wal-g`. Вони безперервно відправляють журнали транзакцій (WAL) до об'єктного сховища (наприклад, AWS S3 або локального кластера MinIO), що дозволяє нам відновити базу даних до будь-якої конкретної мілісекунди в часі.
* **Найпростіший підхід (rsync через SSH):** Найбільш універсальний метод резервного копіювання для загальних файлів. Ми періодично копіюємо дані на інший сервер. Його легко налагодити і він не вимагає нічого, крім безпечних SSH-ключів.
* **Інкрементальна бінарна передача (ZFS Send/Receive):** Для розширених налаштувань ми не копіюємо цілі диски щоночі. Ми використовуємо екстремальну ефективність `zfs send | zfs receive` для потокової передачі лише змінених блоків через SSH на віддалений сервер TrueNAS або в надійне хмарне сховище.
* **Правило "3-2-1":** 3 копії даних, 2 різні типи носіїв, 1 копія повністю на віддаленому майданчику (off-site).

## Висновок

Ми нарешті завершили архітектуру.

* **Рій (The Swarm)** забезпечує м'язи (Обчислення).
* **Шлюз (The Gateway)** забезпечує вхід (Ingress).
* **Кузня (The Forge)** забезпечує швидкість (CI/CD).
* **Сховище (The Vault)** забезпечує пам'ять (Постійність).

Ви більше не сисадмін, який гасить пожежі або вручну підключає кабелі в дата-центрі. Ви — **Системний Архітектор**, який побудував живий організм, що дихає та самокоригується.

Ви можете розгортати оновлення без страху, знаючи, що міграції відбуватимуться автоматично. Ви можете проспати збій жорсткого диска або непрацюючий вузол, знаючи, що планувальник перемістить ваші обчислювальні завдання, а інтерфейс сховища гарантує, що дані підуть слідом. І завдяки блоковим снапшотам та передачі архівів WAL, ви навіть можете проспати, як розробник випадково запускає `DROP TABLE users;` у п'ятницю ввечері.

**Далі буде: "Горизонт: Масштабування до межі та за її межі."**
