# Власна розробка чи готове рішення: Платформи AI-агентів на GCP

> **«Ціни за одиницю ресурсу майже однакові. Рішення полягає не в тому, скільки ви платите за годину, а в тому, за які саме години ви платите — і кому ви платите, коли все ламається».**

Поки ви оцінювали платформи агентів цієї весни, прайс-лист змінився просто у вас під ногами. На Google Cloud Next '26 Vertex AI перетворився на **Gemini Enterprise Agent Platform** — ті самі сервіси, нова назва, жодної міграції. Потім почали з'являтися зміни у тарифікації: використання Agent Gateway стало платним з **13 липня 2026 року**. Sessions та Memory Bank переходять на систему вимірюваної оплати з **1 вересня 2026 року**. Якщо ваша модель витрат була побудована на червневому інвойсі, вона вже неправильна, а за шість тижнів стане неправильною знову.

Ця стаття є фреймворком для прийняття рішень щодо питання, яке зараз ставлять кожній інфраструктурній команді на GCP: ми запускаємо наших агентів на керованій (managed) платформі чи будуємо власне середовище виконання (runtime)? Вона написана для тих, кому доведеться захищати цю відповідь — із цифрами з власних сторінок тарифікації Google, усіма розрахунками та чітко сформульованими компромісами, яких вистачить, щоб відстояти рішення перед радою директорів.

---

Цей матеріал продовжує тему серії **AI Agent Security** та [Оцінки безпеки платформи AI-агентів](#agent-platform-security-assessment): ті статті запитували, *як перевірити наявну платформу*; ця ж запитує, *яку платформу варто обрати*. Ці два питання перетинаються наприкінці — оцінка є способом перевірити будь-який варіант.

Усі наведені нижче ціни є стандартними тарифами за запитом (on-demand list prices) для регіону us-central1, перевіреними за офіційними сторінками тарифів Google у липні 2026 року. Посилання на кожне джерело наведені в розділі «Джерела». Ваші регіони, знижки та узгоджені індивідуальні тарифи відрізнятимуться, але *структура* розрахунків залишиться незмінною.

## 1. «Власна розробка чи покупка» — це хибне питання

Бінарне формулювання не підходить для GCP, оскільки стек агентів — це не один продукт, а три рівні, і кожен має власну відповідь:

**Фреймворк міркування (reasoning framework) є безкоштовним у будь-якому разі.** Agent Development Kit (ADK) має відкритий вихідний код під ліцензією Apache 2.0. Логіка вашого агента — інструменти, інструкції, оркестрація — це переносний код незалежно від місця запуску. Протокол Google A2A є відкритим стандартом під егідою Linux Foundation. Ніхто не продає вам рівень фреймворку, тому припиніть його оцінювати.

**Середовище виконання (runtime) — це і є реальний предмет вибору.** Є три реалістичні кандидати: Agent Engine (кероване середовище виконання всередині Gemini Enterprise Agent Platform), Cloud Run (керовані контейнери, де ви самі будуєте обв'язку для агентів) та GKE з Agent Sandbox (ви повністю володієте всім). Саме тут гроші та контроль вступають у суперечність, і саме цьому присвячена більша частина статті.

**Площина управління (governance plane) здебільшого йде слідом за середовищем виконання.** Agent Registry, Agent Gateway, політики семантичного управління та нова ідентичність агентів IAM (IAM agent identity) постачаються разом із керованою платформою. У власному середовищі виконання вам доведеться збирати еквіваленти з IAM, service mesh та власного реєстру — [Частина 2](#agent-security-part2) серії про безпеку показала, чого це вимагає.

Тож чесне питання звучить не «купувати чи будувати», а **«яким рівнем ми хочемо володіти та скільки нам коштує володіння ним?»** У 2026 році загальноприйнятою відповіддю для великих команд є гібридний підхід — кероване ядро плюс власні компоненти там, де цього вимагають потреби контролю чи оптимізації витрат. Наведений нижче фреймворк покаже, де саме опиняться ваші робочі навантаження.

## 2. Три архітектури

| | **Agent Engine** (готове) | **Cloud Run** (компроміс) | **GKE + Agent Sandbox** (своє) |
|---|---|---|---|
| Що ви розгортаєте | Код ADK / фреймворку | Контейнери, які ви збираєте | Контейнери + конфігурація кластера |
| Сесії та пам'ять | Керовані (Sessions, Memory Bank) | Будуєте самі або інтегруєте наявні | Будуєте самі або інтегруєте наявні |
| Пісочниця виконання коду | Керована | Налаштовуєте самостійно | Agent Sandbox (gVisor), налаштовуєте самі |
| Ідентичність агента | IAM agent identity (SPIFFE, токени з прив'язкою до сертифікатів) | Сервісні акаунти для кожного сервісу | Workload Identity для кожного пода |
| Управління (Governance) | Agent Registry, Gateway, політики | Збираєте самостійно | Збираєте самостійно |
| Власник межі ізоляції | Google (ви не можете її інспектувати) | Google (контейнери для кожної ревізії) | Ви, повністю |
| Операційне навантаження | Мінімальне | Низьке | Робота для інфраструктурної команди |

Одне свідоме упущення: Compute Engine VM немає в цьому списку. [Частина 1](#agent-security-part1) серії про безпеку пояснила, чому віртуальна машина з дефолтним сервісним акаунтом — це місце, де безпека агентів помирає; ті самі аргументи виключають її з порівняння вартості: усе, що вона заощаджує на тарифі, вона витрачає на розширення радіуса ураження (blast radius).

## 3. Моделі тарифікації — за які години ви платите

Ось факт, який повністю змінює розмову про вартість. На папері націнка за керованість майже нульова:

- **Agent Engine:** $0.085 за vCPU-годину, $0.009 за GiB-годину. Посекундна тарифікація, причому **час простою між кроками (turns) не тарифікується**. Безкоштовний ліміт: 50 vCPU-годин та 100 GiB-годин на місяць.
- **Cloud Run (на основі запитів):** $0.000024 за vCPU-секунду активності, що становить **$0.0864 за vCPU-годину** (різниця з Agent Engine менше 2%). Оплата лише під час обробки запитів; «прогріті» мінімальні інстанси (min-instances) у стані спокою коштують близько десятої частини від активного тарифу. Безкоштовно: 2 млн запитів на місяць.
- **GKE Autopilot:** $0.0445 за vCPU-годину та $0.0049 за GiB-годину — приблизно **вдвічі дешевше** за керовані тарифи — плюс фіксована плата за кластер $0.10/годину (~$73/місяць). Однак ви платите за **запити ресурсів подів (pod resource requests) протягом усього часу їх роботи**, а не за фактично використані обчислення.

Ця остання відмінність вирішує все. Agent Engine та Cloud Run тарифікують *активність*. Autopilot тарифікує *зарезервовану потужність (provisioned capacity)*. Робота агента є пульсуючою (bursty) — він думає короткими сплесками, а в перервах чекає на людину. На платформі з оплатою за активність очікування є безкоштовним. На платформі з оплатою за потужність очікування — це і є ваш рахунок.

Додайте два нові пункти витрат для керованого варіанта: Agent Gateway за тарифом 1 vCPU-години ($0.085) на 15 000 викликів API (плата нараховується з 13 липня), а з 1 вересня — Sessions та Memory Bank по $0.30/GiB-місяць за зберігання плюс 1 vCPU-годину на 3 мільйони операцій читання. Окремо вони здаються мізерними, але при великому обсязі трафіку ці SKU потребують особливої уваги, оскільки в червневих моделях витрат їх ще не було.

## 4. Три практичні приклади

Припущення сформульовано, арифметику показано, усі тарифи взяті з розділу «Джерела». «Утилізація» (utilization) означає відношення активного часу обчислень до загальної зарезервованої потужності.

**Малий сценарій — внутрішній агент підтримки.** 1 vCPU / 2 GiB, 500 запитів на день, близько 5 секунд обчислень на кожен. Це ~21 активна vCPU-година та ~42 GiB-години на місяць.

| Архітектура | Місячна вартість | Чому |
|---|---|---|
| Agent Engine | **$0** | У межах безкоштовного ліміту (50 vCPU-h / 100 GiB-h) |
| Cloud Run | **$0** | У межах безкоштовного ліміту (240k vCPU-s) |
| GKE Autopilot | **~$113** | 1 vCPU + 2 GiB под, зарезервований 24/7 ($40) + плата за кластер ($73) |

На малих масштабах це навіть не змагання, і річ не в тарифах — річ у тому, що керовані платформи не тарифікують очікування, а кластер тарифікує. (Якщо це єдиний кластер у вашому платіжному акаунті, кредит безкоштовного ліміту GKE покриє $73, але суть залишається незмінною.)

**Середній сценарій — агент для роботи з клієнтами.** 2 vCPU / 4 GiB на інстанс, 20 000 запитів на день тривалістю близько 6 секунд кожен: 2 000 активних vCPU-годин, 4 000 GiB-годин на місяць.

| Архітектура | Місячна вартість | Чому |
|---|---|---|
| Agent Engine | **~$201** | (2 000 − 50) × $0.085 + (4 000 − 100) × $0.009 |
| Cloud Run | **~$202** | Ті самі активні секунди за тарифом $0.000024/vCPU-s; 600 тис. запитів — безкоштовно |
| GKE Autopilot | **~$232–390** | Залежить від середньої зарезервованої потужності (4–8 vCPU) проти піку у 10 паралельних запитів |

Дві тисячі завантажених vCPU-годин здаються масштабом, на якому володіння власним кластером має окупатися. Це не так — оскільки автоскейлінг ніколи не відстежує пульсуюче навантаження ідеально, і кожна година роботи поду в режимі очікування коштує вам грошей, тоді як в Agent Engine вона безкоштовна. При ~50% утилізації керовані платформи є дешевшими на *будь-якому* масштабі. Це речення підсумовує весь розділ витрат для більшості читачів.

**Великий сценарій — постійно завантажена мультиагентна платформа.** 40 vCPU / 80 GiB безперервно завантажені, 24/7 — платформа, що запускає фонових агентів, а не чекає на людей. 29 200 vCPU-годин на місяць.

| Архітектура | Місячна вартість | Чому |
|---|---|---|
| Agent Engine | **~$3 002** | 29 150 × $0.085 + 58 300 × $0.009 |
| Cloud Run (на основі інстансів) | **~$2 313** | $0.000018/vCPU-s за час життя інстансу |
| GKE Autopilot, за запитом | **~$1 660** | 29 200 × $0.0445 + 58 400 × $0.0049 + $73 |
| GKE Autopilot, 3-річний CUD | **~$946** | Тарифи за зобов'язанням використання (CUD) $0.024475 / $0.0027 |
| GKE Autopilot, Spot | **~$548** | Тарифи Spot $0.0133 / $0.0015 — лише для агентів, що допускають переривання |

Тут аргумент на користь власної розробки (build) стає реальним: на 45% дешевше за Agent Engine за стандартними тарифами, на 69% із зобов'язаннями (CUD) та на 82% на Spot-інстансах для навантажень, які допускають витіснення (preemption). Загальне правило, яке можна вивести з тих самих сторінок: при 100% утилізації точка перетину лежить близько **1 500 vCPU-годин на місяць** — це приблизно два безперервно завантажені vCPU. Кожен відсоток втраченої утилізації зміщує цю точку вгору; при 50% вона не настає ніколи.

Три прості приклади — це лише орієнтир, а не ваша реальна інфраструктура. Щоб прорахувати цю математику для вашої реальної архітектури, я підтримую проєкт [gcp-cost-estimator](https://github.com/d3ep0ps/gcp-cost-estimator) — інструмент із відкритим кодом, який парсить ваш Terraform, звертається до локально кешованої копії публічних тарифів GCP і повертає деталізовану оцінку. Він працює локально та детерміновано — жодна LLM не вигадує ціни, і жоден опис інфраструктури не залишає вашу машину. Тут діє той самий принцип, що й у цій статті: лише цифри, які можна відстежити до опублікованого SKU, або жодних цифр взагалі.

**Чесне застереження:** жодна з цих цифр не враховує вартість роботи людей. Платформа агентів на GKE вимагає спеціалістів для оновлень, безпеки нод, конфігурації пісочниць та реагування на нічні інциденти. Навіть чверть повної вартості роботи інженера платформи становить $3–5 тисяч на місяць, що повністю перекреслює заощадження великого масштабу, доки парк агентів не виросте в кілька разів, і робить власний варіант збитковим на менших масштабах. Таблиця розрахунків нічого не вирішує, доки в ній немає рядка про операційні витрати.

## 5. Контроль, безпека та шлях до виходу

Ціна — це аргумент для всіх; контроль — це те, що дійсно вирішує справу. Проведемо три архітектури через [три межі](https://github.com/d3ep0ps/agent-security-assessment) з нашої оцінки безпеки:

**Досяжність (Reach).** На GKE ви володієте кожним рівнем: gVisor через Agent Sandbox, вихідний трафік заборонений за замовчуванням (default-deny egress), Workload Identity на рівні пода, обмеження Model Armor — кожен із цих елементів можна перевірити командами з оцінки безпеки. В Agent Engine ізоляція є керованою; дослідження Unit 42 «Double Agents», описане в [Частині 1](#agent-security-part1), показало, що відбувається, коли ламається межа, яку ви не могли перевірити. Купівля готового означає довіру до межі, яку ви не бачите зсередини. Це не є критичним недоліком — це просто ризик, який ви оцінюєте, а наша методика покаже, чи мали б ваші власні межі вищу оцінку.

**Ідентичність (Identity).** Тут перевага нещодавно перейшла до готового рішення: IAM agent identity — унікальні для кожного агента принципали SPIFFE з токенами, прив'язаними до сертифікатів (які неможливо повторно використати за межами середовища виконання) — є вбудованою функцією Agent Engine. У вашому власному середовищі виконання еквівалентом є Workload Identity плюс service mesh, що для більшості команд буде в найкращому разі рівнем «Налаштовано» (Configured), тоді як у першому випадку ідентичність є «Примусово» (Enforced) за самою своєю архітектурою.

**Походження та шлях до виходу (Provenance and the exit door).** Питання прив'язки до вендора (vendor lock-in) заслуговує на точний розрахунок, а не просто відчуття:

| Переносне — переживе зміну платформи | Залежне — доведеться створювати заново |
|---|---|
| Код агента ADK (Apache 2.0, працює будь-де) | Конфігурація runtime + ідентичність в Agent Engine |
| Протокол A2A (відкритий стандарт, Linux Foundation) | Sessions (керований сервіс) |
| Agent Sandbox (відкритий код, будь-який K8s кластер) | Memory Bank (керований, включно з версіями) |
| Образи контейнерів, MCP-сервери | Політики Agent Gateway, семантичне управління |
| | Інструменти спостереження та оцінки в консолі |

Закономірність очевидна: Google зробив відкритими ті рівні, які ви все одно написали б самі, і залишив закритими рівні, які накопичують стан (state) — а стан має властивість накопичуватися. Історію сесій можна замінити. **Пам'ять агента — ні**: з 1 вересня ви платитимете за її зберігання, вона стає ціннішою з кожним місяцем роботи, і перш ніж довірити роки цієї пам'яті сервісу Memory Bank, попросіть свою команду продемонструвати реальний шлях її експорту — не прочитати про нього, а саме запустити. Якщо відповіддю на питання «як нам забрати нашу пам'ять» є скликання чергової наради, ви вже отримали свою відповідь про рівень прив'язки (lock-in) — це рівень «Документовано» (Documented).

## 6. Рішення, стисло

**Купувати готове (Agent Engine)**, якщо ваші агенти мають пульсуюче навантаження, взаємодіють із людьми та споживають менше ~1 500 активних vCPU-годин на місяць; якщо у вас немає вільної команди платформи; якщо гарантії безпеки ідентичності агентів є критичними для ваших аудиторів. Прийміть як факт: межу ізоляції ви перевірити не зможете, а стан вашої системи буде накопичуватися за закритим API.

**Компромісний варіант (Cloud Run)**, якщо ви хочете отримувати рахунки лише за фактичну активність, але при цьому контролювати контейнери — наприклад, якщо ви вже запускаєте там інші сервіси, а ваші агенти є достатньо безстановими (stateless), щоб ви могли самі керувати їхніми сесіями. Прийміть як факт: ви взяли на себе всю технічну рутину з налаштування, але не отримали повного контролю на рівні кластера, який би це виправдовував. Зазвичай це проміжний етап, а не кінцева точка.

**Власна розробка (GKE + Agent Sandbox)**, якщо ви маєте постійне високе навантаження на обчислення (кілька безперервно зайнятих vCPU і більше), наявну команду платформи, а також завдання, де можна застосувати Spot-тарифи та знижки за зобов'язаннями (CUD). Прийміть як факт: появу операційного рядка у вашій таблиці витрат та одноосібну відповідальність за кожну межу, яку перевіряє наша оцінка безпеки.

**Тест на чесність, запозичений з будь-якого хорошого архітектурного огляду:** чи зможе ваша команда супроводжувати це як повноцінний продакшн-сервіс — оновлення, чергування (on-call), планування потужностей, виправлення вразливостей — і говорити про це серйозно? Якщо так, власна розробка є життєздатним варіантом. Якщо ні, найдешевший тариф у таблиці вище стане найдорожчим рішенням у цій статті.

І гібридний дефолт, до якого приходить більшість зрілих команд: керована платформа для зовнішніх пульсуючих агентів, GKE для постійного фонового парку агентів, та одна загальна оцінка безпеки, запущена для обох варіантів.

## 7. Перед тим, як підписати угоду

Який би шлях ви не обрали, ви збираєтеся довірити платформі запуск агентів, які діятимуть у ваших системах. Два відкриті інструменти з цього блогу роблять рішення раціональним та вимірюваним: [Оцінка безпеки платформи AI-агентів](https://github.com/d3ep0ps/agent-security-assessment) (сімнадцять перевірок, три межі ізоляції, рівні доказів) показує, що саме ви отримуєте по обидва боки вибору, а [gcp-cost-estimator](https://github.com/d3ep0ps/gcp-cost-estimator) перетворює ваш власний Terraform-код на модель витрат, яку ми тут описали. Запустіть обидва інструменти, і обговорення вибору «своє чи готове» стане дуже коротким: три цифри оцінки безпеки та детальний кошторис, покладені поруч, говоритимуть самі за себе.

Це стандарт, якому має відповідати будь-яке інфраструктурне рішення — включно з тими, для оцінки яких запрошують мене. Команди, які успішно проходять цей вибір — це не ті, хто знайшов найнижчу ціну в таблиці; це ті, хто може надати чіткі докази та обґрунтування свого вибору на першу вимогу.
