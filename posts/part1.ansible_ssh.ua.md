# Чекліст Безпеки Сервера День-1: Захист SSH на Linux та FreeBSD

**Припиніть входити як root. Припиніть вводити паролі. Припиніть довіряти собі "пам'ятати" про безпеку. Автоматизуйте це.**

У нашій попередній статті, ["Досить Клікати: Шлях до Infrastructure as Code,"](https://d3ep0ps.com/#iac) ми навчилися піднімати сервери автоматично, використовуючи інструменти на кшталт Terraform та Vagrant.

Ми побудували інфраструктуру. Тепер ми повинні захистити її.

Існує протверезлива реальність розгортання сервера в публічному Інтернеті: Протягом хвилин після завантаження він буде просканований автоматизованими ботами, що шукають дефолтні облікові дані та слабкі конфігурації.

Це не особисте. Це автоматизовано. І якщо ваш захист покладається на те, що ви вручну пам'ятаєте відредагувати конфіг-файли на кожному новому сервері, ви врешті-решт зазнаєте невдачі.

Безпека — це не "додаток" на потім. Це вимога "Дня-1", яка має бути "запечена" у вашу автоматизацію.

Ця стаття є Частиною 1 серії з двох частин про захист Unix-систем. Чи розгортаєте ви Ubuntu Linux, чи запускаєте захищений FreeBSD jail, принципи ідентичності однакові. Сьогодні ми фокусуємося на **Рівні Ідентичності та Доступу**: захисті того, *хто* може увійти і *як*, використовуючи SSH та Ansible.

## ⚠️ Правила Взаємодії: Прочитайте Це Спочатку

Перш ніж ми почнемо, важливе попередження. Ми збираємося модифікувати основний спосіб вашого доступу до сервера (SSH).

**Помилки тут катастрофічні.** Одруківка в конфіг-файлі SSH може повністю заблокувати вам доступ. Немає кнопки "скасувати", як тільки з'єднання розірвано. Вам, ймовірно, доведеться знищити сервер і почати спочатку.

> ..... або використовувати серійну консоль. :) 

Слідуйте цим правилам, щоб залишатися в безпеці:

1.  **Ніколи не працюйте спочатку на продакшен сервері.** Використовуйте локальну VM (наприклад, Vagrant) або одноразовий хмарний інстанс для тестування ваших плейбуків.
2.  **Завжди тримайте одну root-сесію відкритою.** Перед застосуванням змін, які перезапускають SSH, тримайте одне активне термінальне з'єднання відкритим до сервера. Якщо ви заблокуєте себе, ця існуюча сесія може бути вашим єдиним шляхом назад, щоб виправити це.
3.  **Перевіряйте свій доступ негайно.** Після застосування будь-яких змін відкрийте *нове* вікно терміналу і спробуйте увійти. Не закривайте вашу оригінальну сесію, доки не підтвердите, що нова конфігурація працює.
4.  **Використовуйте функції безпеки Ansible.** Ми будемо використовувати команди валідації в наших плейбуках, щоб перевірити синтаксис конфіг-файлу перед перезапуском сервісів. Не видаляйте їх.

## Фаза 1: Локальна Підготовка (Рівень Ідентичності)

Ми не можемо автоматизувати створення вашої приватної ідентичності. Це єдиний ручний крок, який ви повинні зробити на вашій локальній машині, щоб встановити, *хто ви є*. У вас є дві опції для генерації ключів.

### Опція A: Стандарт (Програмні Ключі Ed25519)

Якщо ви все ще використовуєте 2048-бітні RSA ключі, час оновитися. Сучасним стандартом для програмних ключів є **Ed25519**. Він менший, швидший і безпечніший за старі типи.

На вашій локальній машині (macOS, Linux або BSD) згенеруйте нову пару ключів:

```bash
ssh-keygen -t ed25519 -C "your_email@example.com"
```

### Опція B: Золотий Стандарт (Апаратні Ключі FIDO)

Для найвищого рівня безпеки використовуйте апаратний ключ безпеки, такий як YubiKey.

Сучасні версії OpenSSH підтримують токени FIDO/U2F нативно. Коли ви генеруєте цей тип ключа, приватний криптографічний матеріал генерується на апаратному пристрої і **ніколи не залишає його**.

Щоб увійти, ви повинні мати фізичний пристрій, підключений до вашого комп'ютера, *і* фізично торкнутися його, щоб підтвердити вашу присутність. Це робить віддалену крадіжку ваших ключів практично неможливою.

Щоб згенерувати апаратний ключ (переконайтеся, що ваш токен підключений):

```bash
# '-sk' означає Security Key
ssh-keygen -t ecdsa-sk -C "yubikey_2025"
```

*(Примітка: На macOS або деяких дистрибутивах Linux вам може знадобитися встановити специфічні бібліотеки middleware, такі як `libfido2`, щоб ця команда працювала.)*

### Важливість Парольних Фраз (Passphrases)

Яку б опцію ви не обрали, промпт запитає парольну фразу. **Не пропускайте це.**

Приватний ключ SSH без парольної фрази — це просто файл. Якщо хтось вкраде ваш ноутбук, вони володіють вашими серверами. Сильна парольна фраза шифрує ключ у стані спокою.

### Життя з Парольними Фразами (ssh-agent)

Безпека бореться зі зручністю. Вводити довгу парольну фразу кожного разу, коли ви підключаєтеся по SSH, дратує. Рішенням є **SSH Agent**, який тримає ваш розшифрований ключ безпечно в пам'яті для вашої сесії.

  * Завантажте ноутбук.
  * Запустіть `ssh-add` і введіть вашу парольну фразу один раз.
  * Працюйте весь день, не вводячи її знову.

## Проблема "Bootstrap": Потрапити Всередину Вперше

Перш ніж ми подивимося на код Ansible, ми повинні вирішити поширену проблему курки і яйця.

Щоб запустити плейбук Ansible, який захищає сервер, Ansible спочатку повинен мати можливість увійти на цей сервер з існуючими адміністративними правами.

Кожне середовище починається по-різному:

  * **Локальні VM (Vagrant):** Зазвичай надають користувача `vagrant` з попередньо налаштованим sudo без пароля.
  * **VPS Провайдери (напр., DigitalOcean):** Часто надають `root` логін, або з надісланим на email паролем, або з SSH-ключем, який ви вибрали під час створення.
  * **Хмарні Платформи (напр., GCP, AWS):** Ці платформи використовують інструмент під назвою **cloud-init**, який запускається при першому завантаженні. Він читає метадані, які ви надаєте (наприклад, ваш публічний ключ SSH), і налаштовує дефолтного користувача (напр., `ubuntu`, `ec2-user`), щоб ви могли увійти.

**Це ваш "Bootstrap User".**

Ви використаєте цього початкового, часто небезпечного користувача рівно один раз: щоб запустити плейбук посилення безпеки (hardening playbook). Мета плейбука — використати цей тимчасовий доступ, щоб створити вашого персоналізованого, безпечного адмін-користувача, а потім грюкнути дверима перед небезпечними методами bootstrap.

В інструкціях до лабораторії нижче ви побачите, де налаштувати цього bootstrap користувача у файлі інвентаря Ansible, щоб він знав, як зробити це найперше з'єднання.

## Фаза 2: Підхід Ansible до Управління Користувачами

З Ansible ми визначаємо бажаний стан наших користувачів у YAML. Цей підхід працює безшовно як на Linux, так і на FreeBSD. Нам потрібен не-root адмін-користувач із встановленим вашим Публічним SSH Ключем.

Посилення SSH — це не про параною.
Це про видалення людської помилки з рівняння.
Системи повинні "fail closed" (закриватися при збої), а не "fail open". Автоматизація ідентичності — це перший крок до передбачуваної, безпечної інфраструктури.

```yaml
# vars/main.yml
admin_user: "d3ep0ps_admin"
# Вставте вміст вашого ЛОКАЛЬНОГО ~/.ssh/id_ed25519.pub (або id_ecdsa_sk.pub) сюди
admin_ssh_pub_key: "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI..."

# playbook.yml tasks
- name: Ensure admin user exists
  user:
    name: "{{ admin_user }}"
    # На Linux група 'sudo' зазвичай дає права адміна.
    # На FreeBSD ви зазвичай додаєте користувачів до групи 'wheel'.
    groups: "{{ 'wheel' if ansible_facts['os_family'] == 'FreeBSD' else 'sudo' }}"
    shell: /bin/sh
    append: yes
    state: present

- name: Deploy SSH public key for admin user
  authorized_key:
    user: "{{ admin_user }}"
    state: present
    key: "{{ admin_ssh_pub_key }}"
```

## Фаза 3: Посилення Демона (sshd\_config as Code)

## 🚨 НЕБЕЗПЕЧНА ЗОНА: Конфігурація SSH

**Попередження:** Ця секція модифікує конфігурацію демона SSH. Якщо ви зробите помилку і SSH перезапуститься, ви будете заблоковані. Переконайтеся, що ви дотримувалися "Правил Взаємодії" вище.

Нам потрібно відредагувати `/etc/ssh/sshd_config`, щоб забезпечити два критичні налаштування:

1.  **`PasswordAuthentication no`**: Відхиляти *будь-яку* спробу увійти з паролем.
2.  **`PermitRootLogin no`**: Змусити зловмисників вгадати валідне ім'я користувача *і* мати приватний ключ цього користувача.

Ми використовуємо модуль Ansible `lineinfile`, щоб безпечно редагувати файл, і **handler** (обробник), щоб перезапустити демон SSH тільки якщо відбулася зміна.

```yaml
# playbook.yml tasks
- name: Disable Password Authentication
  lineinfile:
    path: /etc/ssh/sshd_config
    regexp: '^#?PasswordAuthentication'
    line: 'PasswordAuthentication no'
    # Команда validate перевіряє синтаксис ДО збереження, запобігаючи багатьом блокуванням
    validate: '/usr/sbin/sshd -t -f %s'
  notify: Restart SSH

- name: Disable Root Login
  lineinfile:
    path: /etc/ssh/sshd_config
    regexp: '^#?PermitRootLogin'
    line: 'PermitRootLogin no'
    validate: '/usr/sbin/sshd -t -f %s'
  notify: Restart SSH

# handlers/main.yml
- name: Restart SSH
  service:
    name: sshd
    state: restarted
```

*(Зверніть увагу на команду `validate`. Це критична функція безпеки. Вона запускає `sshd -t` (тестовий режим) проти нового конфіг-файлу. Якщо є синтаксична помилка, Ansible впаде і НЕ збереже зламаний файл, рятуючи вас від блокування.)*
