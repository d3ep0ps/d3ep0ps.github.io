# Кузня: Безперервна Інтеграція та Автоматизований Конвеєр

> **"Якщо людина повинна торкатися цього, щоб розгорнути, — процес зламаний."**

Ми провели останні кілька статей, будуючи самовідновлюваний кластер (Рій — The Swarm) і парадний вхід (Шлюз — The Gateway). Але робота архітектора не закінчується, коли інфраструктура "піднята". Вона закінчується, коли система може **еволюціонувати** з великою швидкістю без втручання людини.

Досі ми говорили про те, *де* все працює (Nomad, Jails, Docker). Тепер ми поговоримо про те, *як* воно туди потрапляє. Ми переходимо від ручних операцій до **Все як Код** (Everything as Code).

## 1. Стратегія: Швидкість як Архітектурна Ціль

У застарілому середовищі розгортання — це повільна, ручна "Подія". Але нещодавно я виступав як **Системний Архітектор** і **DevOps Інженер** під час **Хакатону**, де ми мали 4 тижні на створення системи промислового рівня. У нас не було часу на ручні SSH-сесії. Щоб перемогти, нам потрібна була швидкість.

На тому Хакатоні ми використовували **Kubernetes (GKE)**, оскільки це був найшвидший шлях до керованого середовища. У нашій домашній лабораторії ми використовуємо **Nomad**. Краса **Кузні (The Forge)** полягає в тому, що *патерн* залишається ідентичним, незалежно від рушія.

Я впровадив **Кузню** не лише для порядку, а й для швидкості. Коли ваш конвеєр повністю автоматизований, час між "Ідеєю" та "Живим Сервісом" скорочується з годин до хвилин. Це не просто технічний вибір; це конкурентна перевага.

## 2. Креслення: Розділені Репозиторії

Професійна Кузня вимагає чітких кордонів. У своїй реалізації я розділив зони відповідальності на три окремі шари, щоб гарантувати, що зміна в одному не зламає інші:

1. **Інфраструктурний Шар (Terraform):** Виділений простір для "фундаменту". Цей код визначає вузли, приватні мережі та пули ресурсів. Відокремлюючи це від програми, ми гарантуємо стабільність апаратного рівня.
2. **Глобальний Мережевий Репо:** Окремий репозиторій високого рівня для "Парадних Дверей". Це керує **Шлюзом (Ingress)**, **Балансувальником Навантаження**, сертифікатами **Let’s Encrypt** та глобальними **HTTP маршрутами**. Він діє як центральна політика того, як світ досягає нашого кластера.
3. **Шар Застосунку (Monorepo):** Містить код мікросервісу разом із спеціальною папкою `deployment/`. Коли код змінюється, конвеєр точно знає, як запакувати сервіс і оновити його конкретний слід у кластері.

## 3. Механіка Конвеєра

Використовуючи **GitLab CI** та **Google Cloud Build**, процес дотримується суворого правила "Без Людей":

* **Збірка (The Build):** Кузня виковує код у **Незмінний Артефакт** (Immutable Artifact). Для Linux це Docker Image. Для FreeBSD ми використовуємо автоматизацію, наприклад `bastille bootstrap`, щоб створити чистий, версіонований шаблон Jail.
* **Реєстр (The Registry):** Образ надсилається до приватної зброярні. Ми ніколи не розгортаємо "сирий код"; ми розгортаємо лише версіоновані, протестовані образи.
* **Розгортання (The Deployment):** Кузня застосовує специфікації завдання.

### Універсальний Патерн: K8s проти Nomad

Незалежно від того, чи використовуєте ви галузевий стандарт Kubernetes (як ми на Хакатоні) або ефективний стек Nomad (як ми в D3ep0ps), крок "Розгортання" виглядає дивовижно схожим. Це просто текстовий файл, що описує бажаний стан.

**Спосіб Хакатону (Kubernetes):**
Ми визначили маніфест `Deployment`. Це багатослівний, але стандартний підхід.

```yaml
# k8s/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api-service
  template:
    metadata:
      labels:
        app: api-service
    spec:
      containers:
      - name: api
        image: gcr.io/my-project/api-service:v1.2.0
        ports:
      - containerPort: 8080
```

**Спосіб D3ep0ps (Nomad):**
У нашій домашній лабораторії ми досягаємо того ж результату з меншою кількістю шаблонного коду, використовуючи Nomad.

```hcl
# nomad/api-service.nomad
job "api-service" {
  group "api" {
    count = 3
    task "server" {
      driver = "docker"
      config {
        image = "my-registry/api-service:v1.2.0"
        ports = ["http"]
      }
    }
  }
}
```

В обох випадках **Кузня** робить те саме: вона оновлює версію `image` у файлі та надсилає його до API кластера. Кластер бере на себе решту.

## 4. Безпека та Секрети: Зсув Вліво (Shift Left)

Оскільки Кузня є єдиним шляхом до продакшну, вона стає нашим головним пунктом перевірки безпеки. Ми не просто "ховаємо" секрети; ми повністю усуваємо доступ людей до них.

**Принцип "Нульового Дотику Людини":**
У традиційному налаштуванні системний адміністратор може вручну скопіювати файл `.env` на сервер. Це вразливість. У **Кузні** конвеєр є дійсним *лише* в тому випадку, якщо він може розгортатися без людини, яка тримає ключі.

**На Хакатоні (Google Secret Manager):**
Ми використовували хмарний підхід.

1. **Зберігання:** Секрети (паролі БД, ключі API) зберігалися в **Google Secret Manager**.
2. **Синхронізація:** Ми встановили **External Secrets Operator** у Kubernetes.
3. **Виконання:** Оператор автоматично отримував секрети з GCP і створював об'єкти K8s `Secret`, які монтувалися в наші події як змінні середовища.

**У Лабораторії D3ep0ps (HashiCorp Vault):**
Для нашої приватної інфраструктури ми використовуємо золотий стандарт: **HashiCorp Vault**.
Замість синхронізації секретів *у* кластер, Nomad інтегрується безпосередньо з Vault. Коли завдання запускається, воно запитує тимчасові, динамічні облікові дані, які існують *лише* протягом життя цього процесу.

В обох архітектурах розробник ніколи не вносить пароль у репозиторій, а оператор ніколи його не бачить. Секрет існує лише тоді, коли він потрібен програмі.

## Висновок

Кузня — це серце літери "D" у **DevOps**. Вона заповнює прогалину між **Розробкою (Development)** та **Операціями (Operations)**.

З працюючою Кузнею:

* **Вартова Вежа** (Observability) повідомляє нам, чи здорова нова збірка.
* **Рій** (Orchestration) займається розгортанням.
* **Шлюз** (Ingress) направляє користувачів до нової версії на основі глобальної політики маршрутизації.

Ми побудували машину, яка будує сама себе. Але є одна остання, часто ігнорована частина подорожі. У нас є вся ця сила для переміщення сервісів... але як нам поводитися з **Базою Даних**, не втрачаючи дані в процесі?
