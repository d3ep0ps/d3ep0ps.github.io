# TLS з перших принципів: Як інтернет навчився зберігати таємниці

> **"Шифрування — це не про приховування чогось ганебного. Це про право на приватну розмову у світі, повному незнайомців."**

У статті **The Gateway (Шлюз)** ми налаштували Traefik для термінації TLS на межі нашого кластера. У статті **Mail Server (Поштовий сервер)** ми наказали Postfix і Dovecot "використовувати TLS" і пішли далі. В обох випадках ми використовували технологію, не пояснюючи її досконало.

Сьогодні ми це виправимо.

До кінця цієї статті ви не просто знатимете, *як встановити* сертифікат. Ви зрозумієте, *чому вся ця система працює* — що таке сертифікат насправді, хто його підписує і чому це важливо, і як браузер та сервер домовляються про секретний ключ на очах у всього інтернету так, щоб ніхто не зміг його викрасти.

Потім ми візьмемо це розуміння і застосуємо його систематично: Apache, Nginx, Postfix, Dovecot, Kubernetes та GCP. Одна ментальна модель. Кожен рівень стеку.

## 1. Проблема: Інтернет народився довірливим

Ранній інтернет будували науковці, що ділилися дослідженнями. Ніхто не намагався вкрасти чиїсь паролі, бо паролів, вартих крадіжки, майже не було.

HTTP — Hypertext Transfer Protocol — був розроблений у тому світі. Це протокол відкритого тексту. Кожен байт, який ви надсилаєте через HTTP, подорожує крізь роутери, кабелі та комутатори у форматі, який може прочитати будь-яка машина на шляху.

Щоб побачити, наскільки це небезпечно, запустіть це у вашій локальній мережі, поки хтось підключається до сайту через HTTP:

```bash
# Від імені root — захоплення HTTP-трафіку на інтерфейсі
sudo tcpdump -i eth0 -A 'tcp port 80' | grep -i 'password\|user\|login\|cookie'
```

Ви побачите облікові дані у відкритому вигляді. Не як теоретичну вправу, а як живу демонстрацію. Саме так працюють атаки в кав'ярнях. Так працює збір даних у готельних Wi-Fi. Саме тому HTTP фактично мертвий для всього, що має значення.

Три загрози, для подолання яких розроблено TLS, є чіткими:

**Прослуховування (Eavesdropping)** — пасивний зловмисник читає ваш трафік, не втручаючись. Ви ніколи не дізнаєтесь, що він там був. Ваші cookie сесії, приватні повідомлення, API-ключі — все як на долоні.

**Втручання (Tampering)** — активний зловмисник стає між вами та сервером ("Man-in-the-Middle") і змінює дані під час передачі. Він може впровадити шкідливий JavaScript на сторінку, змінити суму банківського переказу або замінити завантаження програмного забезпечення на вірус — і без TLS ні ви, ні сервер не матимете жодного способу це виявити.

**Імітація (Impersonation)** — зловмисник запускає сервер, який *стверджує*, що він є вашим банком. Без способу перевірки особи ваш браузер не має механізму, щоб відрізнити справжній сервер від підробки.

TLS — Transport Layer Security — вирішує всі три проблеми одночасно. Він забезпечує **конфіденційність** (шифрування перемагає прослуховування), **цілісність** (коди автентифікації повідомлень перемагають втручання) та **автентифікацію** (сертифікати перемагають імітацію).

## 2. Як працює TLS: три акти

Розуміння TLS вимагає розуміння трьох ідей, що будуються одна на одній. Кожна з них проста. Разом вони елегантні.

### Акт I — Асиметричний замок

Класичне симетричне шифрування використовує один ключ: той самий ключ шифрує і дешифрує. Якщо ви хочете зашифрувати повідомлення для друга, вам обом потрібен однаковий ключ — і ви стикаєтеся з класичним парадоксом: *як спочатку безпечно поділитися цим ключем?* Якби ви могли поділитися секретом через незахищений канал, вам би не знадобився ключ.

Асиметрична криптографія (з "відкритим ключем") вирішує цей парадокс за допомогою хитрого трюку: вона використовує *два математично пов'язані ключі*. Те, що один зашифровує, тільки інший може розшифрувати — і знання одного ключа нічого не дає для розуміння іншого.

Уявіть це як навісний замок:

- **Відкритий ключ (public key)** — це *відкритий замок*. Ви роздаєте копії всім охочим. Будь-хто може замкнути його на повідомленні.
- **Закритий ключ (private key)** — це *єдиний ключ, який його відкриває*. Ви тримаєте його в секреті, завжди, назавжди.

Якщо хтось хоче надіслати вам секрет, він кладе його в скриньку і замикає вашим відкритим замком. Тепер *тільки ви* можете її відкрити. Навіть той, хто щойно її замкнув, не може її знову відкрити.

Саме так ваш браузер надсилає секрет серверу, ніколи не передаючи сам секрет.

### Акт II — Рукостискання (Handshake)

Рукостискання TLS — це переговори, які відбуваються до того, як буде передано хоча б один байт ваших фактичних даних. Воно займає мілісекунди та виконує три речі: узгодження алгоритмів шифрування, автентифікація ідентичності сервера та встановлення спільного секретного ключа — і все це через незашифрований канал.

Ось спрощена схема сучасного рукостискання TLS 1.3:

```
Клієнт                                          Сервер
  |                                               |
  |──── ClientHello ──────────────────────────>   |
  |     (Набори шифрів, ключові частки, Random)   |
  |                                               |
  |   <──── ServerHello + Certificate ────────    |
  |     (Обраний шифр, ключова частка,            |
  |      сертифікат сервера, Finished)            |
  |                                               |
  |  [Клієнт перевіряє сертифікат і генерує       |
  |   спільний секрет]                            |
  |                                               |
  |──── Finished ──────────────────────────────>  |
  |                                               |
  |  <=== Зашифровані дані додатка ====>          |
```

Етап обміну ключами заслуговує на окрему увагу. Використовуючи **обмін ключами Діффі-Геллмана**, клієнт і сервер кожен генерують тимчасову пару ключів, обмінюються відкритими значеннями та математично поєднують їх зі своїм власним закритим значенням. Результат — на обох сторонах незалежно — ідентичний спільний секрет. Прослуховувач, який записав кожен байт цього обміну, не може вивести секрет, оскільки він ніколи не бачив жодного закритого значення.

З цього моменту все спілкування зашифровано швидким симетричним шифром (зазвичай AES-256-GCM), використовуючи спільний секрет як ключ. Асиметрична криптографія використовувалася лише для рукостискання; основна робота з шифрування великих обсягів даних виконується симетрично.

### Акт III — Сертифікат та ланцюжок довіри

У наведеному вище рукостисканні залишається одна невирішена проблема: коли сервер представляє свій відкритий ключ, як клієнт дізнається, що він належить *справжньому* серверу, а не імітатору?

Це робота **сертифіката**.

TLS-сертифікат — це документ, який пов'язує відкритий ключ з ідентичністю (доменним ім'ям). Важливо, що цей документ **цифрово підписаний** — це означає, що довірена третя сторона криптографічно підтвердила його.

Структура являє собою ланцюжок:

```
Кореневий сертифікат (Root CA)
  └── Проміжний сертифікат (Intermediate CA) (підписаний Кореневим)
        └── Ваш сертифікат сервера (підписаний Проміжним)
```

**Кореневі центри сертифікації (Root CAs)** — це організації, чиї відкриті ключі попередньо встановлені у вашій операційній системі та браузері — Mozilla, Google, Apple та Microsoft підтримують такі списки. Ви довіряєте їм за замовчуванням, бо ваш постачальник ОС перевірив їх.

**Проміжні центри (Intermediate CAs)** існують для безпеки: закриті ключі Root CA зберігаються офлайн у сховищах. Повсякденне підписування здійснюється Проміжними центрами, які були підтверджені Кореневим.

**Ваш сертифікат** підписаний Проміжним. Коли ваш браузер отримує його, він проходить по ланцюжку: *"Чи довіряє Проміжний X цьому сертифікату? Чи довіряє Кореневий Y Проміжному X? Чи є Кореневий Y у моєму сховищі довіри?"* Якщо всі три перевірки пройдено, ідентичність підтверджено.

Окрім ланцюжка, браузер перевіряє шість речей для кожного сертифіката:

1. **Термін дії** — мітки часу `Not Before` та `Not After`. Прострочені сертифікати жорстко відхиляються.
2. **Відповідність імені хоста** — домен у сертифікаті повинен відповідати домену, на який ви перейшли (поле `CN` або `Subject Alternative Names`).
3. **Валідність підпису** — криптографічний підпис повинен успішно перевірятися відкритим ключем видавця.
4. **Повнота ланцюжка** — кожна ланка в ланцюжку повинна бути валідною та довіреною.
5. **Відкликання** — сертифікат не повинен бути у списку відкликаних (CRL або відповідь OCSP).
6. **Журнали Certificate Transparency** — сучасні браузери вимагають, щоб сертифікати реєструвалися в публічних журналах CT, що робить неможливим видачу сертифіката для домену без публічного аудиту.

Якщо будь-яка з цих перевірок не проходить, браузер показує червоне попередження. Тільки при проходженні всіх шести з'являється зелений замочок.

## 3. Ландшафт сертифікатів: хто що підписує

Тепер, коли ми розуміємо, що таке сертифікат, постає питання: *хто має підписати ваш?*

### Самопідписані сертифікати (Self-Signed)

Самопідписаний сертифікат — це сертифікат, де видавцем є *ви самі*. Ви генеруєте пару ключів, створюєте сертифікат і підписуєте його власним закритим ключем. Ланцюжка довіри немає — тільки ваше слово, що ви той, за кого себе видаєте.

```bash
# Генерація самопідписаного сертифіката, дійсного 365 днів
openssl req -x509 -nodes -days 365 \
  -newkey rsa:2048 \
  -keyout /etc/ssl/private/self.key \
  -out /etc/ssl/certs/self.crt \
  -subj "/CN=internal.d3ep0ps.local"
```

Браузери будуть попереджати користувачів. Зовнішні клієнти відхилятимуть їх за замовчуванням. Але самопідписані сертифікати цілком доречні в кількох ситуаціях: внутрішні сервіси в приватній мережі, mTLS між сервісами всередині кластера Kubernetes (де ви контролюєте всіх клієнтів) та середовища розробки.

Золоте правило: якщо ви контролюєте *всіх* клієнтів, самопідписаний сертифікат — це нормально. Якщо підключатиметься будь-який зовнішній клієнт, вам потрібен сертифікат, підписаний CA.

### Комерційні центри сертифікації (Платні сертифікати)

До появи Let's Encrypt єдиним способом отримати довірений браузером сертифікат була оплата послуг CA. Вони все ще існують, і для деяких випадків це все ще правильна відповідь.

Комерційні CA пропонують три рівні перевірки:

**Domain Validation (DV)** — CA перевіряє, що ви контролюєте домен (через DNS-запис або файл на сервері). Це той самий рівень, що й у Let's Encrypt. Ви платите за зручність довших термінів дії та іноді за впізнаваність бренду, але рівень безпеки ідентичний безкоштовному сертифікату.

**Organisation Validation (OV)** — CA додатково перевіряє, що ваша організація юридично існує (реєстраційні документи, телефонна перевірка). Сертифікат містить назву вашої компанії. Коштує дорожче, але надає ідентичність бізнесу, що підлягає аудиту.

**Extended Validation (EV)** — найсуворіша перевірка. Раніше відображалася як зелений рядок адреси з назвою компанії. Сучасні браузери здебільшого відмовилися від цієї візуальної відмінності, що значно знизило цінність EV.

Чесна відповідь: для вебсерверів сертифікати Let's Encrypt DV зараз є професійним стандартом. Сертифікати OV/EV варто розглядати для фінансових або державних сервісів з високими вимогами до комплаєнсу, де важлива офіційна перевірка організації.

### Let's Encrypt: революція ACME

Let's Encrypt, запущений у 2016 році, — це некомерційний центр сертифікації, який видає DV-сертифікати безкоштовно, автоматично та в масовому масштабі. Зараз це найбільший CA у світі за кількістю виданих сертифікатів, який фундаментально змінив індустрію.

Автоматизація базується на **протоколі ACME** (Automatic Certificate Management Environment), який зараз є стандартом IETF (RFC 8555). ACME працює через видачу **виклику (challenge)**: CA просить ваш сервер довести контроль над доменом одним із двох способів:

- **HTTP-01**: Надати доступ до специфічного файлу за адресою `http://yourdomain.com/.well-known/acme-challenge/<token>`
- **DNS-01**: Створити DNS TXT запис `_acme-challenge.yourdomain.com` з певним значенням

Після проходження виклику CA видає сертифікат. Весь процес займає секунди й повністю автоматизується такими інструментами, як **Certbot**.

Сертифікати Let's Encrypt дійсні **90 днів**. Це свідоме безпекове рішення, а не обмеження. Короткочасні сертифікати обмежують вікно шкоди від скомпрометованого ключа — якщо ваш закритий ключ вкрадено, вікно зловмисника становить максимум 90 днів, а не роки. Вони також змушують до автоматизації: ви не зможете підтримувати парк 90-денних сертифікатів вручну, тому ви змушені впроваджувати правильне управління життєвим циклом сертифікатів з першого дня.

### Порівняння з першого погляду

| | Самопідписаний | Комерційний DV | Let's Encrypt | Комерційний OV/EV |
|---|---|---|---|---|
| **Вартість** | Безкоштовно | $10–$200/рік | Безкоштовно | $100–$1000+/рік |
| **Довіра браузера** | ❌ (попередження) | ✅ | ✅ | ✅ |
| **Автоматизація** | Вручну | Вручну/API | Повністю авто | API (варіюється) |
| **Термін дії** | Будь-який | 1 рік | 90 днів | 1–2 роки |
| **Перевірка особи** | Немає | Тільки домен | Тільки домен | Домен + Організація |
| **Найкраще для** | Внутрішні/Dev | Застарілі системи | Все публічне | Фінанси/Комплаєнс |

## 4. TLS через весь стек

TLS — це не тільки про HTTPS. Це транспортний рівень безпеки для майже кожного протоколу, що передає чутливі дані. Ментальна модель завжди однакова — рукостискання, сертифікат, спільний секрет — але деталі залежать від протоколу.

### Веб (HTTPS)

Коли ви переходите на `https://d3ep0ps.com`, ваш браузер виконує повне рукостискання, описане в розділі 2. Вебсервер (Apache або Nginx) термінує TLS, дешифрує ваш запит і відповідає. У кластерній архітектурі, як наша, TLS термінується на **Шлюзі (The Gateway)** (Traefik або Nginx), а не на кожному окремому сервісі — це робить внутрішній трафік легшим.

HTTPS за домовленістю працює на **порту 443**. Порт 80 (HTTP) варто тримати лише для перенаправлення на 443:

```nginx
server {
    listen 80;
    server_name d3ep0ps.com;
    return 301 https://$host$request_uri;
}
```

### Пошта (STARTTLS проти Implicit TLS)

Пошта — це місце, де TLS стає заплутаним, бо існують два різні механізми та три порти.

**STARTTLS** — це механізм оновлення. Клієнт підключається через порт відкритого тексту (25 для SMTP між серверами, 587 для відправлення клієнтом) і видає команду `STARTTLS` посеред сесії, щоб оновити з'єднання до TLS. З'єднання починається як незашифроване і стає зашифрованим.

**Implicit TLS** (іноді називають "TLS-wrapped" або "SMTPS/IMAPS") починає TLS негайно, ще до того, як будуть передані будь-які команди протоколу. Це сучасний рекомендований підхід.

| Порт | Протокол | Метод TLS | Використання |
|---|---|---|---|
| 25 | SMTP | STARTTLS | Передача між серверами |
| 465 | SMTPS | Implicit TLS | Відправлення клієнтом (preferred) |
| 587 | SMTP Submission | STARTTLS | Відправлення клієнтом |
| 993 | IMAPS | Implicit TLS | Доступ клієнта IMAP |
| 995 | POP3S | Implicit TLS | Доступ клієнта POP3 |

Ми налаштували Postfix і Dovecot у статті **Mail Server**. У розділі 5.2 нижче ми додамо правильний TLS до цього стеку.

### DNS over TLS (DoT)

У статті про **BIND DNS** ми запускали авторитативний та рекурсивний резолвер. Стандартний DNS (порт 53) також є протоколом відкритого тексту — ваші DNS-запити повідомляють спостерігачу, які саме сайти ви відвідуєте, навіть якщо ці сайти працюють через HTTPS.

**DNS over TLS** (DoT, порт 853) огортає DNS-запити в стандартну сесію TLS, забезпечуючи конфіденційність та цілісність. **DNSSEC** (про який ми згадували у статті про BIND) — це інший і доповнювальний механізм: DNSSEC підписує DNS-*відповіді*, щоб запобігти втручанню в самі дані, але він не шифрує їх. DoT та DNSSEC вирішують різні проблеми й мають використовуватися разом.

Налаштування BIND для DoT вимагає TLS-сертифіката та директиви `listen-on` з увімкненим `tls`:

```bash
# Фрагмент /etc/named.conf
options {
    listen-on port 853 tls local-tls { any; };
};

tls local-tls {
    cert-file "/etc/letsencrypt/live/dns.d3ep0ps.com/fullchain.pem";
    key-file  "/etc/letsencrypt/live/dns.d3ep0ps.com/privkey.pem";
};
```

## 5. Практика: Let's Encrypt через весь стек

### 5.1 — Веб: Apache та Nginx із Certbot

**Встановлення Certbot:**

```bash
sudo apt update
sudo apt install -y certbot python3-certbot-nginx python3-certbot-apache
```

**Для Nginx — автоматичний режим:**

Плагін `--nginx` від Certbot зчитує вашу існуючу конфігурацію Nginx, отримує сертифікат і змінює конфіг для ввімкнення TLS — і все це однією командою:

```bash
sudo certbot --nginx -d d3ep0ps.com -d www.d3ep0ps.com
```

Certbot запитає вашу електронну адресу (для повідомлень про закінчення терміну дії), попросить погодитися з умовами та автоматично обробить виклик HTTP-01. Після успіху він перепише ваш блок сервера приблизно так:

```nginx
server {
    listen 443 ssl;
    server_name d3ep0ps.com www.d3ep0ps.com;

    ssl_certificate     /etc/letsencrypt/live/d3ep0ps.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/d3ep0ps.com/privkey.pem;

    # Certbot додає це для сильної конфігурації TLS:
    include /etc/letsencrypt/options-ssl-nginx.conf;
    ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem;

    # Далі ваші існуючі блоки location...
}

# Перенаправлення HTTP → HTTPS (також додається автоматично):
server {
    listen 80;
    server_name d3ep0ps.com www.d3ep0ps.com;
    return 301 https://$host$request_uri;
}
```

**Для Apache — автоматичний режим:**

```bash
sudo certbot --apache -d d3ep0ps.com -d www.d3ep0ps.com
```

Плагін `--apache` аналогічно зчитує конфігурацію VirtualHost і автоматично створює новий VirtualHost з підтримкою TLS.

**Перевірка сертифіката:**

```bash
# Перевірка робочого сертифіката ззовні
openssl s_client -connect d3ep0ps.com:443 -servername d3ep0ps.com </dev/null 2>/dev/null \
  | openssl x509 -noout -dates -subject -issuer
```

Ви повинні побачити свій домен у полі subject, Let's Encrypt як видавця та вікно дії ~90 днів від сьогодні.

**Тестування автоматичного оновлення:**

Certbot встановлює таймер systemd (або cron-задачу), яка запускається двічі на день і оновлює будь-який сертифікат, термін дії якого закінчується протягом 30 днів. Перевірте роботу конвеєра оновлення:

```bash
sudo certbot renew --dry-run
```

Успішний запуск "dry run" означає, що ваша автоматизація оновлення працює. Запускайте це після будь-яких системних змін, які можуть на це вплинути (правила фаєрвола, перевантаження вебсервера, зміна портів).

**Керування оновленням та перезавантаженням:**

Критична деталь: після оновлення сертифіката вебсервер потрібно **перезавантажити (reload)**, щоб він побачив нові файли.

- Якщо ви використовували плагіни `--nginx` або `--apache`, Certbot виконує це перезавантаження автоматично.
- Якщо ви використовували `certonly` або ручний метод, вам потрібен хук оновлення (renewal hook), подібний до того, що ми налаштуємо для поштового сервера в наступному розділі:

```bash
# Приклад додавання ручного хука перезавантаження, якщо не використовуються плагіни
sudo certbot renew --deploy-hook "systemctl reload nginx"
```

### 5.2 — Пошта: Postfix + Dovecot

Гарна новина: **вам не потрібен другий сертифікат**. Той самий сертифікат Let's Encrypt, виданий для вашого поштового домену (`mail.d3ep0ps.com`), підходить і для Postfix, і для Dovecot. Отримайте його один раз:

```bash
# Використовуйте режим standalone, якщо вебсервер не запущений на цьому хості,
# або --nginx/--apache, якщо запущений (вкажіть ваш поштовий домен)
sudo certbot certonly --standalone -d mail.d3ep0ps.com
```

Сертифікат з'явиться за адресою `/etc/letsencrypt/live/mail.d3ep0ps.com/`.

**Налаштування Postfix (SMTP):**

Відредагуйте `/etc/postfix/main.cf` та додайте або оновіть директиви TLS:

```ini
# /etc/postfix/main.cf

# TLS для вхідних з'єднань (STARTTLS на портах 25 та 587)
smtpd_tls_cert_file = /etc/letsencrypt/live/mail.d3ep0ps.com/fullchain.pem
smtpd_tls_key_file  = /etc/letsencrypt/live/mail.d3ep0ps.com/privkey.pem
smtpd_tls_security_level = may          # пропонувати TLS, але не вимагати для вхідних
smtpd_tls_loglevel = 1                  # логування рукостискань TLS

# TLS для вихідних з'єднань (коли Postfix надсилає на інші сервери)
smtp_tls_cert_file = /etc/letsencrypt/live/mail.d3ep0ps.com/fullchain.pem
smtp_tls_key_file  = /etc/letsencrypt/live/mail.d3ep0ps.com/privkey.pem
smtp_tls_security_level = may           # використовувати TLS, якщо віддалений сервер підтримує його
smtp_tls_loglevel = 1

# Вимкнення застарілих протоколів
smtpd_tls_protocols = !SSLv2, !SSLv3, !TLSv1, !TLSv1.1
smtp_tls_protocols  = !SSLv2, !SSLv3, !TLSv1, !TLSv1.1
```

Увімкніть порт submission (587) зі STARTTLS у `/etc/postfix/master.cf` — розкоментуйте або додайте:

```
submission inet n - y - - smtpd
  -o syslog_name=postfix/submission
  -o smtpd_tls_security_level=encrypt
  -o smtpd_sasl_auth_enable=yes
  -o smtpd_client_restrictions=permit_sasl_authenticated,reject
```

Перезавантажте Postfix:

```bash
sudo systemctl reload postfix
```

**Налаштування Dovecot (IMAP/POP3):**

Відредагуйте `/etc/dovecot/conf.d/10-ssl.conf`:

```ini
# /etc/dovecot/conf.d/10-ssl.conf

ssl = required                          # вимагати TLS для всіх з'єднань

ssl_cert = </etc/letsencrypt/live/mail.d3ep0ps.com/fullchain.pem
ssl_key  = </etc/letsencrypt/live/mail.d3ep0ps.com/privkey.pem

# Вимкнення застарілих протоколів
ssl_min_protocol = TLSv1.2

# Вибір сильних шифрів
ssl_cipher_list = ECDHE+AESGCM:ECDHE+CHACHA20:!aNULL:!eNULL:!EXPORT
ssl_prefer_server_ciphers = yes
```

Перезавантажте Dovecot:

```bash
sudo systemctl reload dovecot
```

**Перевірка Postfix STARTTLS:**

```bash
openssl s_client -connect mail.d3ep0ps.com:587 -starttls smtp
```

Ви побачите рукостискання, деталі сертифіката, а потім потрапите в SMTP-сесію. Шукайте `250-STARTTLS` у вітанні сервера та ваш сертифікат Let's Encrypt у виводі ланцюжка.

**Перевірка Dovecot IMAPS:**

```bash
openssl s_client -connect mail.d3ep0ps.com:993
```

Успішне з'єднання покаже сертифікат та вітання IMAP (`* OK Dovecot ready`).

**Керування оновленням сертифіката для Postfix та Dovecot:**

Certbot оновлює сертифікати автоматично, але Postfix та Dovecot потрібно перезавантажити, щоб вони побачили нові файли. Додайте хук оновлення:

```bash
# /etc/letsencrypt/renewal-hooks/deploy/reload-mail.sh
#!/bin/bash
systemctl reload postfix
systemctl reload dovecot
```

```bash
sudo chmod +x /etc/letsencrypt/renewal-hooks/deploy/reload-mail.sh
```

Certbot запускає всі скрипти в `renewal-hooks/deploy/` після кожного успішного оновлення. Поштовий стек завжди матиме свіжий сертифікат без ручного втручання.

### 5.3 — Kubernetes: cert-manager на GKE

У кластері Kubernetes ви не запускаєте Certbot. Керування життєвим циклом сертифікатів здійснюється **cert-manager** — нативним контролером Kubernetes, який стежить за ресурсами `Certificate` та `Issuer` і автоматизує весь процес ACME, зберігаючи результат у `Secret` Kubernetes.

**Крок 1 — Встановлення cert-manager через Helm:**

```bash
# Додавання репозиторію Helm Jetstack
helm repo add jetstack https://charts.jetstack.io
helm repo update

# Встановлення cert-manager з інсталяцією CRD
helm install cert-manager jetstack/cert-manager \
  --namespace cert-manager \
  --create-namespace \
  --set installCRDs=true
```

Переконайтеся, що всі три поди запущені:

```bash
kubectl get pods -n cert-manager
```

**Крок 2 — Створення ClusterIssuer (спочатку staging):**

Завжди починайте з середовища staging Let's Encrypt. Стейджинг-CA не є довіреним для браузерів, але ліміти запитів там значно лояльніші. Протестуйте тут, а потім переходьте на production.

```yaml
# cluster-issuer-staging.yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-staging
spec:
  acme:
    server: https://acme-staging-v02.api.letsencrypt.org/directory
    email: some_email@d3ep0ps.com
    privateKeySecretRef:
      name: letsencrypt-staging-key
    solvers:
    - http01:
        ingress:
          class: nginx   # або 'gce' для стандартного Ingress у GKE
```

```bash
kubectl apply -f cluster-issuer-staging.yaml
```

Коли стейджинг запрацює, створіть production issuer:

```yaml
# cluster-issuer-prod.yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: some_email@d3ep0ps.com
    privateKeySecretRef:
      name: letsencrypt-prod-key
    solvers:
    - http01:
        ingress:
          class: nginx
```

```bash
kubectl apply -f cluster-issuer-prod.yaml
```

**Крок 3 — Анотування вашого Ingress:**

Найпростіший спосіб використовувати cert-manager — анотувати існуючий ресурс Ingress. cert-manager помітить анотацію, автоматично створить ресурс `Certificate` та запустить процес ACME:

```yaml
# ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: d3ep0ps-ingress
  annotations:
    # Вказуємо cert-manager, який issuer використовувати
    cert-manager.io/cluster-issuer: "letsencrypt-prod"
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - d3ep0ps.com
    - www.d3ep0ps.com
    secretName: d3ep0ps-tls    # cert-manager створить і заповнить цей Secret
  rules:
  - host: d3ep0ps.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: d3ep0ps-svc
            port:
              number: 80
```

**Крок 4 — Спостереження за роботою cert-manager:**

```bash
# Стеження за ресурсом Certificate
kubectl get certificate -w

# Перевірка процесу запиту сертифіката
kubectl describe certificaterequest
```

Ресурс `Certificate` перейде зі стану `False` у `True` в колонці `Ready` протягом 60–90 секунд. cert-manager потім автоматично оновлює його за 30 днів до закінчення терміну дії.

### 5.4 — GCP: Google-Managed Certificates

GCP пропонує альтернативу cert-manager для кластерів GKE, що використовують нативний Ingress від GKE (на базі Google Cloud Load Balancer): **Google-managed certificates**.

З керованими сертифікатами GCP бере на себе весь життєвий цикл — підготовку, оновлення та ротацію — з нульовою конфігурацією з вашого боку, окрім вказівки домену.

**Варіант А — Ресурс ManagedCertificate для GKE Ingress:**

```yaml
# managed-cert.yaml
apiVersion: networking.gke.io/v1
kind: ManagedCertificate
metadata:
  name: d3ep0ps-managed-cert
spec:
  domains:
    - d3ep0ps.com
    - www.d3ep0ps.com
```

Вкажіть його в анотації вашого Ingress:

```yaml
# ingress-gcp.yaml
metadata:
  annotations:
    networking.gke.io/managed-certificates: "d3ep0ps-managed-cert"
    kubernetes.io/ingress.class: "gce"    # Тільки для нативного Ingress GKE
```

**Варіант Б — Cloud Run (нульова конфігурація):**

Якщо ваш сервіс працює на **Cloud Run**, TLS на вашому кастомному домені повністю автоматичний. Ви просто мапите домен, підтверджуєте право власності через DNS-запис, і GCP зробить усе інше.

## 6. Операційна дисципліна: ніколи не дозволяйте сертифікату закінчитися

Закінчення терміну дії сертифіката в продакшені — один із найбільш безглуздих інцидентів, яких найлегше уникнути. І водночас один із найпоширеніших. Сценарій завжди однаковий: сертифікат оновили вручну, людина, яка про це знала, звільнилася, і ніхто нічого не помічав, поки браузери не почали показувати червоні попередження.

Правильна відповідь — це архітектура, а не пильність: **автоматизуйте оновлення так, щоб людина ніколи не була в цьому ланцюжку**.

### Сповіщення Prometheus про закінчення терміну дії

Навіть з автоматичним оновленням вам потрібна система раннього попередження. Додайте це правило сповіщення до вашої конфігурації Prometheus:

```yaml
# prometheus/rules/tls.yml
groups:
- name: tls
  rules:
  - alert: TLSCertificateExpiringSoon
    expr: ssl_certificate_expiry_seconds{} < 86400 * 14
    for: 1h
    labels:
      severity: warning
    annotations:
      summary: "TLS сертифікат скоро закінчиться на {{ $labels.instance }}"
      description: >
        Сертифікат для {{ $labels.domain }} закінчується через
        {{ $value | humanizeDuration }}. Можливо, автоматичне оновлення не спрацювало.
```

Це вимагає `ssl_exporter` або `blackbox_exporter` для отримання метрики `ssl_certificate_expiry_seconds`. Попередження за 14 днів дає вам два тижні на розслідування, чому автоматика не спрацювала.

## 7. Що ми побудували

Почавши з мережі відкритого тексту та трьох конкретних загроз, ми пройшли через математичні основи TLS — асиметричне шифрування, рукостискання Діффі-Геллмана, ланцюжок довіри — і застосували це на кожному рівні стеку:

- **Apache та Nginx** тепер термінують HTTPS з автоматично оновлюваними сертифікатами Let's Encrypt.
- **Postfix та Dovecot** шифрують як відправлення клієнтом, так і передачу між серверами, з автоматичним перезавантаженням при оновленні.
- **Kubernetes (GKE)** керує життєвим циклом сертифікатів через cert-manager без участі людини.
- **GCP** пропонує керовані сертифікати для Cloud Load Balancer та Cloud Run.

Паттерн у кожному випадку однаковий: довіра не припускається, вона доводиться криптографічно; а оновлення — це не подія в календарі, а системна властивість автоматизації.

## Що далі

Коли транспортна безпека налаштована на всіх рівнях, постає наступне питання: *а що насправді всередині ваших контейнерів?* TLS-сертифікат доводить, з ким ви розмовляєте. Він нічого не каже про те, чи можна довіряти коду, що працює на тому сервері.

У статті **Security as Code: SBOM та ланцюжок постачання** ми розглянемо безпеку ланцюжка постачання ПЗ — генерацію Software Bill of Materials, сканування образів на вразливості за допомогою `trivy`, підписування образів Cosign та інтеграцію всього цього в **The Forge**, щоб безпека забезпечувалася на етапі збірки, а не виявлялася в продакшені.
