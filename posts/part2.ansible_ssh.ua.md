# Чекліст Безпеки Сервера День-1: Побудова Периметра на Linux та FreeBSD

**Вийдіть за межі ключів. Заглушіть шум, заблокуйте ботів і автоматизуйте ваш мережевий захист.**

У **Частині 1** цієї серії, ["Чекліст Безпеки Сервера День-1: Захист SSH,"](https://d3ep0ps.com/#part1_ansible_ssh) ми захистили **Рівень Ідентичності**. Ми забезпечили, що єдиний спосіб увійти на ваш сервер — це криптографічно безпечний ключ, і що обліковий запис root недоступний через SSH.

Парадні двері вашого сервера мають замок, який неможливо зламати відмичкою.

Але шлях до цих дверей видимий для всього Інтернету. Щохвилини автоматизовані сканери смикають ручку, тестуючи порт 22, заповнюючи ваші логи невдалими спробами аутентифікації. Цей шум маскує реальні загрози і витрачає ресурси сервера.

Настав час побудувати стіну навколо сервера і поставити охоронця біля воріт.

У **Частині 2** ми фокусуємося на **Мережевому Периметрі**. Ми реалізуємо "захист у глибину" (defense in depth), змінивши дефолтний порт SSH, розгорнувши фаєрвол з політикою "default-deny" (UFW на Linux, PF на FreeBSD) і налаштувавши активний захист за допомогою Fail2Ban, все автоматизовано з Ansible.

## ⚠️ Правила Взаємодії: Прочитайте Це Спочатку

Перш ніж ми почнемо, критичне попередження. Ми збираємося змінити порт, який ви використовуєте для підключення до вашого сервера, і увімкнути систему, призначену для блокування мережевого трафіку.

**Помилки тут катастрофічні.** Якщо ви зміните порт SSH у конфігу, але забудете відкрити його у фаєрволі, або якщо ви увімкнете фаєрвол до того, як дозволите SSH, **ви заблокуєте себе повністю.** Немає кнопки "скасувати", як тільки з'єднання розірвано.

Слідуйте цим правилам, щоб залишатися в безпеці:

1.  **Ніколи не працюйте спочатку на продакшен сервері.** Використовуйте локальну VM (наприклад, Vagrant) або одноразовий хмарний інстанс для тестування ваших плейбуків.
2.  **Завжди тримайте одну root-сесію відкритою.** Перед застосуванням змін, які перезапускають SSH або вмикають фаєрвол, тримайте одне активне термінальне з'єднання відкритим до сервера. Якщо ви заблокуєте себе, ця існуюча сесія може бути вашим єдиним шляхом назад, щоб виправити це.
3.  **Порядок має значення.** У нашій автоматизації ми повинні переконатися, що новий порт SSH дозволений у фаєрволі *до того*, як ми змінимо конфігурацію SSH і перезапустимо сервіс.
4.  **Перевіряйте свій доступ негайно.** Після застосування будь-яких змін відкрийте *нове* вікно терміналу і спробуйте увійти на новому порту. Не закривайте вашу оригінальну сесію, доки не підтвердите, що нова конфігурація працює.

## 1\. Великі Дебати: Зміна Порту SSH

Перш ніж ми торкнемося фаєрволу, ми повинні розглянути найпоширеніший і найсуперечливіший перший крок у посиленні безпеки сервера: зміна порту SSH з дефолтного `22` на щось інше (наприклад, `2222` або `5757`).

Критики стверджують, що це "безпека через неясність" (security through obscurity). Вони мають рацію. Рішучий зловмисник просканує весь ваш сервер і знайде SSH, де б ви його не сховали. Зміна порту не зупинить цілеспрямовану атаку.

**То чому ми це робимо?**

Ми робимо це заради **співвідношення сигнал/шум**.

99% атак, що б'ють по вашому серверу, — це тупі скрипти, що сканують весь адресний простір IPv4 на предмет порту 22. Перемістивши ваш сервіс SSH на високий, нестандартний порт, ви миттєво зникаєте з радарів цих низькопробних ботів.

Ваші логи переходять від тисяч невдалих спроб входу на годину до майже нуля. Це означає, що коли ви *все ж таки* бачите невдалий логін у ваших логах, ви знаєте, що це реальна аномалія, варта розслідування. Це перетворює шум на сигнал.

### Реалізація Ansible

Зміна порту — це просте редагування `/etc/ssh/sshd_config`, за яким слідує перезапуск сервісу. Ми використовуємо змінну для номера порту, щоб його було легко змінити пізніше.

```yaml
# playbook.yml snippet
- name: Change SSH port to a non-standard port
  lineinfile:
    path: /etc/ssh/sshd_config
    regexp: '^#?Port\s+'
    line: "Port {{ ssh_custom_port }}"
    validate: '/usr/sbin/sshd -t -f %s'
  notify: Restart SSH
```

## 2\. Філософія Фаєрволу: Default Deny

Фаєрвол — це ваш цифровий прикордонник. Він інспектує кожен мережевий пакет, що намагається увійти або вийти з вашого сервера.

Найкритичніша концепція в дизайні фаєрволу — це політика **Default Deny** (Заборонити за Замовчуванням).

  * **Погана Політика (Default Allow):** Все дозволено, крім речей, які я явно блокую. (Це важко керувати і небезпечно).
  * **Хороша Політика (Default Deny):** Все заблоковано, крім специфічного трафіку, який я явно дозволяю.

Ми налаштуємо наші фаєрволи так, щоб відкидати всі вхідні запити на з'єднання за замовчуванням, а потім просвердлимо єдиний, точний отвір для нашого нестандартного порту SSH.

## 3\. Реалізація Linux: UFW (Uncomplicated Firewall)

На Linux (зокрема Ubuntu/Debian, нашій цілі), базовий фаєрвол ядра складний (`nftables` або `iptables`). Щоб зробити його керованим, ми використовуємо шар абстракції під назвою **UFW**.

UFW розроблений бути простим і читабельним для людини. Він ідеально відповідає етосу "спокійної інженерії".

### Підхід Ansible

Ansible має чудовий вбудований модуль для UFW, який робить декларативну конфігурацію легкою. Зверніть увагу на порядок: ми дозволяємо нестандартний порт *до того*, як увімкнути фаєрвол.

```yaml
# roles/firewall_linux/tasks/main.yml
---
- name: Ensure UFW is installed
  apt:
    name: ufw
    state: present

- name: Set default policies (Default Deny)
  community.general.ufw:
    policy: deny
    direction: incoming

- name: Allow outgoing traffic
  community.general.ufw:
    policy: allow
    direction: outgoing

- name: Allow SSH on custom port
  community.general.ufw:
    rule: allow
    port: "{{ ssh_custom_port }}"
    proto: tcp
    comment: "Allow custom SSH access"

# Критично: Увімкнути фаєрвол останнім, після встановлення правил.
- name: Enable UFW firewall
  community.general.ufw:
    state: enabled
```

## 4\. Реалізація FreeBSD: PF (Packet Filter)

FreeBSD використовує інший підхід. Їй не потрібні "нескладні" обгортки, тому що її нативний фаєрвол, **PF (Packet Filter)**, легендарний своїм чистим, читабельним і потужним синтаксисом конфігурації.

На відміну від Linux, де ми використовуємо модуль Ansible для запуску команд, на FreeBSD ми керуємо фаєрволом, шаблонізуючи його конфігураційний файл напряму. Це підкреслює ключову відмінність в управлінні двома ОС.

### Підхід Ansible

Ми визначаємо наші правила у файлі шаблону (`pf.conf.j2`) і розгортаємо його в `/etc/pf.conf`.

**Шаблон (`templates/pf.conf.j2`):**

```pf
# /etc/pf.conf - Managed by Ansible

# Macros
# Визначити зовнішній інтерфейс динамічно
ext_if = "{{ ansible_default_ipv4.interface }}"
# Використати нашу змінну нестандартного порту
ssh_port = "{{ ssh_custom_port }}"

# Options
set block-policy drop
set skip on lo0

# Normalization
scrub in on $ext_if all fragment reassemble

# --- ЗОЛОТЕ ПРАВИЛО: DEFAULT DENY ---
# Блокувати все, що входить, за замовчуванням
block in all
# Дозволити весь трафік, що виходить
pass out all keep state

# Просвердлити отвір: Дозволити SSH на нашому кастомному порту
pass in on $ext_if proto tcp from any to any port $ssh_port keep state
```

**Завдання Плейбука:**
Ми використовуємо модуль `template`, щоб розгорнути файл, і handler, щоб перезавантажити PF. Ми також повинні переконатися, що сервіс PF увімкнено в `/etc/rc.conf`.

```yaml
# roles/firewall_freebsd/tasks/main.yml
---
- name: Enable PF in rc.conf
  service:
    name: pf
    enabled: yes

- name: Deploy PF configuration template
  template:
    src: pf.conf.j2
    dest: /etc/pf.conf
    mode: '0600'
    # КРИТИЧНО: Валідувати синтаксис перед збереженням, щоб запобігти блокуванням!
    validate: 'pfctl -nf %s'
  notify: Reload PF
```

## 5\. Активний Захист: Fail2Ban

Ми перемістили SSH і побудували фаєрвол. Наші логи стали тихішими, і відкритий лише один порт.

Але зловмисники все ще можуть знайти цей порт і почати перебирати ключі. Статичне правило фаєрволу дозволяє їм пробувати вічно. Нам потрібен активний захист. Нам потрібен вишибала.

**Fail2Ban** — це той вишибала. Він моніторить лог-файли (наприклад, логи аутентифікації), шукаючи патерни невдач. Якщо IP-адреса не може увійти занадто багато разів за короткий період, Fail2Ban динамічно оновлює фаєрвол (UFW або PF), щоб забанити цю IP-адресу на встановлений час.

### Підхід Ansible

Ми встановлюємо Fail2Ban і розгортаємо локальний конфігураційний файл, який визначає наші правила "jail" (в'язниці).

```yaml
# roles/fail2ban/tasks/main.yml
---
- name: Ensure Fail2Ban is installed
  package:
    name: fail2ban
    state: present

- name: Deploy Fail2Ban jail configuration
  template:
    src: jail.local.j2
    dest: /etc/fail2ban/jail.local
  notify: Restart Fail2Ban
```

У нашому шаблоні ми кажемо Fail2Ban моніторити SSH на нашому новому *кастомному порту*.
